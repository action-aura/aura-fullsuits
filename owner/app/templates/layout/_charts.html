Hand-rolled, zero external dependency, colors exclusively via var(--aura-*) tokens (tokens.css) so dark mode / RTL need no separate code path, same discipline as every other component in components.css/shell.css. Tone vocabulary matches .badge's own: default/success/warning/danger/pending (see components.css's .badge.* groupings) -- callers should not invent a new tone name. -- Interactivity pass (Dashboard Interactive Kit, stage 2) -------------- Hover/focus highlighting, cross-highlighting between a donut segment and its legend row, and the per-datapoint value readout below are implemented in CSS ONLY (charts.css). No JS file is involved, on purpose: every effect here is a pure projection of DOM state (:hover / :focus-within / :has()), so there is nothing for a script to own, nothing to re-bind after a re-render, and nothing that breaks when JS is unavailable. The markup below only has to supply the two things CSS cannot derive on its own: 1. a real focus target for every data point (a drill-down where one genuinely exists, otherwise a tabindex="0" element) -- without it the readout could only ever appear on mouse hover, and the keyboard parity bar this branch's a11y stage set would not be met; and 2. a stable `data-slice` index shared by a donut segment and its legend row, which is what lets a CSS :has() rule light up the one from the other (see charts.css's "cross-highlight" block for the documented 8-slice ceiling that costs -- CSS has no loops, so each pairing is a hand-written rule). The readout element itself is aria-hidden: its text is character-for- character the same string already exposed as the focus target's accessible name (aria-label), so exposing both would make a screen reader announce the same sentence twice on a single focus move. Sighted hover/focus gets the visual bubble; assistive tech gets the accessible name.
