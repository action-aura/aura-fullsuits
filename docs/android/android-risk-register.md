# Android Migration Risk Register (Phase 4)

| ID | Risk | Likelihood/Impact | Mitigation taken this phase | Residual status |
|---|---|---|---|---|
| R1 | Splitting `BuildConfig.FLAVOR`-branched files (`AppRoot.kt`, `DashboardScreen.kt`, `SetupScreen.kt`) could accidentally drop functionality for the kept product. | Medium / Medium | Rewrote each file by removing only the *other* product's branch, keeping the target product's logic byte-for-byte where unrelated to the flavor check; no new UI text or routes invented. | Not verified by an automated diff against the source per-flavor build (no such build exists to diff against) — verified by manual read-through and by the parity matrices' route/screen inventory. |
| R2 | Android's `main.py` depended on `aura_core`, which doesn't exist in `aura-fullsuits`. A naive port could silently change server startup behavior (env resolution order, seeding, port selection). | High / High | New `main.py` follows the *already-shipped and regression-tested* `products/{retail,clinic}/desktop/launcher_{retail,clinic}.py` pattern (same `AURA_BUNDLE_DIR`/`AURA_APP_DATA`/`AURA_STANDALONE` env vars, same `_find_free_port`/waitress-in-thread approach), not a fresh design. `config.py` in both backends already natively supports these env vars (used identically by the desktop launcher). | Contract with Kotlin (`start_server`/`wait_until_ready`/`server_port`) preserved unchanged, so `ServerBootstrap.kt` needed zero edits. Not yet exercised on a real device/emulator (see build reports) — Gradle build success confirms it compiles and packages, not that the server actually answers on-device. |
| R3 | Chaquopy pip dependency list was trimmed from the monolith's full `requirements.txt` down to only what each product's backend imports. A missed transitive import could crash the server at runtime with `ModuleNotFoundError`. | Medium / High | Trim was based on an exhaustive `grep` of every `import`/`from` statement across `products/{retail,clinic}/backend/` and `commercial_runtime/` (see `android-dependency-map.md`), not guesswork. | Only verified at Python *syntax*/pip-install level (Gradle build success = packages installed, sources merged) — not verified by actually running the Flask app inside Chaquopy on a device, since no emulator is available this phase. Documented as a device-testing follow-up. |
| R4 | Bundle assets (`assets/bundle/**`, extracted by `AssetInstaller.java` on first run) could be empty, which would make `AssetInstaller.installIfNeeded()` throw (`AssetManager.list()` returns empty/null on a genuinely empty dir → falls into the "copy as file" branch → `FileNotFoundException`), crashing `ServerBootstrap.start()` on first launch. | Medium / High | `stageAuraAssets` Gradle task stages the real, existing `products/{retail,clinic}/frontend/**` (locale JSON + i18n JS files) into `assets/bundle/`, so the directory is always non-empty. `AssetInstaller.java` itself was reused verbatim (no logic change). | Not exercised on-device (no emulator). If a future product ever has a genuinely empty frontend dir, this same failure mode would recur — worth a defensive check in `AssetInstaller.java` in a later phase, out of scope here. |
| R5 | Package/namespace rename (`com.actionaura.enterprise` → `.retail`/`.clinic`) via bulk `sed` could miss references in non-`.kt`/`.java` files (build files, ProGuard rules). | Low / Medium | Verified with a full grep after rename: zero leftover `com.actionaura.enterprise` in either tree. `proguard-rules.pro` in both products was manually checked/fixed (the bulk rename initially missed `.pro` files). | Resolved. |
| R6 | Camera/barcode (CameraX + ML Kit) behavior cannot be verified without a physical device or emulator with camera support — a common area for silent regressions (permission flow, duplicate-scan suppression, offline model loading). | High likelihood of *being untestable this phase* / High impact if broken | None beyond static code review — `BarcodeScanner.kt` was copied verbatim into retail only, with only the package name changed. | **Explicitly deferred to device-validation phase.** No claim of "camera scanning verified" is made anywhere in this phase's output — see the retail parity matrix, marked `REQUIRES PHYSICAL DEVICE VALIDATION`. |
| R7 | Signing: shipping an accidentally-unsigned or debug-signed "release" build, or leaking a keystore/password into version control. | Low likelihood / High impact | `keystore.properties` is git-ignored (`.gitignore` updated to the two-project layout); `release` buildType only applies `signingConfig` if `keystore.properties` exists on disk; only a `.template` file (no real secrets) is committed; no real keystore was generated or used in this phase. | Release builds produced this phase (if any) are **unsigned** by construction — see `signing-and-release-guide.md`. No production signing key exists yet. |
| R8 | The `staging` build type is new (not in source). A misconfigured custom build type can fail to resolve dependencies published only for `debug`/`release` variants. | Medium / Medium | Used AGP's documented `matchingFallbacks = ['debug']` mechanism, `initWith debug` to inherit a known-working base config, then overrode only `applicationIdSuffix`/`debuggable`/`BUILD_ENV`. | Verified by a real Gradle build for the `staging` variant (see build reports) — not just assumed correct. |
| R9 | No physical Android device or emulator is installed in this build environment. | Certain / High for anything requiring runtime UI interaction | None — cannot be mitigated within this phase. All device/emulator-dependent verification (camera, on-device server reachability, gesture navigation, RTL rendering, restart persistence) is explicitly marked `REQUIRES PHYSICAL DEVICE VALIDATION` rather than claimed as tested. | Open — carried into the final response's honesty section and both parity matrices. |
| R10 | Independence proof: an Android build could silently succeed by reading files from the original `AuraEnterprise` repo if a staging task's path were ever wrong (e.g. a copy-paste `repoRoot` left pointing at the old location). | Low likelihood given the paths were authored fresh / High impact if true | Both `stageAuraPython`/`stageAuraAssets` tasks compute `suiteRoot` from `rootProject.projectDir.parentFile.parentFile` (i.e. `aura-fullsuits`, not `AuraEnterprise`) and only reference `products/`/`commercial_runtime/` under it. Static grep + build-log path inspection performed as part of independence verification (see the final response and `android-migration-plan.md`). | See independence-verification results in the final response for the actual commands/output. |
