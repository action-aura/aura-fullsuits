# Android Signing & Release Guide

Applies to both `android/aura-retail/` and `android/aura-clinic/` (each is signed
independently — they are separate apps with separate identities, and **must never
share a signing key** in production, since that would let one app's update silently
carry the other's signature).

not reuse the Retail one. Until then a Clinic `assembleRelease` is unsigned

A release built without `keystore.properties` on disk is **unsigned** (or carries
only a debug signature). Never describe such a build as a "signed release"; see
`android-{retail,clinic}-build-report.md` for exactly what each build was signed with.

## Setting up a signing key (a new product, or rebuilding the setup on a new machine)

1. Generate the keystore **once**, and reuse it for every future update — Android
   only preserves a user's app data across an update if the new APK is signed with
   the *same* key as the installed one. Losing the key means you can never update
   that app again for existing installs, only ship a new listing.

   ```
   keytool -genkeypair -v -keystore aura-release.jks -alias aura \
           -keyalg RSA -keysize 2048 -validity 10000
   ```

2. Copy `keystore.properties.template` (in each product's root, e.g.
   `android/aura-retail/keystore.properties.template`) to `keystore.properties` in
   that same directory, and fill in the real `storeFile`/`storePassword`/`keyAlias`/
   `keyPassword`. This file is git-ignored (`android/*/keystore.properties` in
   `.gitignore`) — never commit it.

3. Store the `.jks` file and its passwords in a secure secrets manager /
   password-protected backup, outside this repository entirely. If a signing key is
   ever exposed (e.g. accidentally committed), rotate it and treat every keystore
   password it protected as compromised.

4. Build the signed release:

   ```
   cd android/aura-retail   # or aura-clinic
   ./gradlew assembleRelease
   ```

   `app/build.gradle`'s `release` buildType only applies `signingConfigs.release` if
   `keystore.properties` exists on disk — with no keystore present, `assembleRelease`
   still succeeds but produces an **unsigned** APK (useful for compile/lint
   verification, not for distribution).

## Never do this

- Never commit `keystore.properties`, any `.jks`/`.keystore` file, or a real
  signing password to this repository (`.gitignore` blocks the common patterns, but
  double-check `git status`/`git diff` before committing anything under `android/`).
- Never expose signing secrets in build logs, chat, or documentation — build reports
  in this repo redact them by construction (they simply state whether a key was
  present, never its contents).
- Never sign `aura-retail` and `aura-clinic` releases with the same keystore — they
  are independent products with independent update lineages.
- Never force-push over, or reuse, a lost signing key by regenerating a keystore with
  the same alias/passwords — Android identifies a key by its certificate fingerprint,
  not by filename; a regenerated keystore is a *different* key even with identical
  metadata.

## Build channels

| Build type | `debuggable` | `applicationIdSuffix` | Signing | Intended use |
|---|---|---|---|---|
| `debug` | true | `.debug` | Android's default debug key (auto-generated by AGP, not a secret) | Local development, `adb install` |
| `staging` | false | `.staging` | Same as `release` (falls back to unsigned if no `keystore.properties`) | Install-and-verify testing before a real release |
| `release` | false | (none) | `keystore.properties` if present, else unsigned | Production distribution — only once a real key is configured |

See `environment-configuration.md` for what else differs (endpoint placeholders,
logging level) between these three.
