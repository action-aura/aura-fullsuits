# Phase 4 — Corrective-Pass Risk Register

Status: **PROVEN** where marked, honest uncertainty elsewhere. Supplements
(does not replace) `docs/android/android-risk-register.md`'s R1-R10 from
the original migration, all of which remain valid and were not re-verified
in this phase unless noted.

| ID | Risk | Status this phase |
|---|---|---|
| R11 | Readiness-check bug (bare `/` polling) present in both `main.py` files, identical to Phase 3.7's Windows finding | **FIXED, source-verified**. Cannot be runtime-verified on-device (no device/emulator available) — the fix mirrors the Windows fix exactly (same `/api/health` target, same monotonic clock) and is regression-guarded by `ReadinessContractTest.kt` in both projects. |
| R12 | Android checkout displayed a locally-computed, untaxed total as if it were the sale's authoritative result | **FIXED**. `SaleResult` now carries the full authoritative contract; the checkout success path reads `r.data.total`. Verified by 3 dedicated Kotlin contract tests (`SaleContractTest.kt`), not yet verified against a real running embedded server (no device). |
| R13 | No client-side idempotency-key on Retail returns or Clinic payments — a double-tap had no dedup protection at the Android layer (the server-side idempotency check still worked *if* a key was sent, but none ever was) | **FIXED**. Both requests now require a real generated `UUID`. |
| R14 | Two `print(f'...{e}')` statements in `clinic_api.py`'s best-effort accounting-sync blocks could leak patient/lab-test names into Logcat via a SQL-bind exception message | **FIXED**. Replaced with type-only logging. This is backend code shared by both products' staged Python — the 279-test backend suite was rerun (required, since this file was modified) and passed unchanged. |
| R15 | Extracting `isDuplicateScan()`/`findProductByCode()` out of Compose lambdas could subtly change behavior (e.g. capture semantics, closure timing) | **Low, mitigated**: both extractions are literal copy-outs of the exact same expression with no logic change, verified by a successful `compileDebugKotlin` and by dedicated unit tests exercising the extracted functions directly. Not verified against the real camera/scanner UI (no device). |
| R16 | Widening `CreatePaymentResponse`'s new `ClinicPaymentResult` class name collided conceptually with the pre-existing (unrelated) `PaymentResult`/`PaymentResultResponse` used by Retail-derived AR endpoints still declared (but not used for billing) in Clinic's `AuraApi.kt` | **Resolved by distinct naming** (`ClinicPaymentResult`), not by removing the unrelated dead endpoints (out of scope — pre-existing, not part of this phase's mandate, not confirmed dead-vs-reachable from any UI). |
| R17 | No physical Android device or emulator installed in this environment (`adb devices` returns empty; no `emulator` package under the Android SDK) | **Certain, unmitigated**. All device/emulator-dependent verification is marked `NOT TESTED`/`SOURCE REVIEW ONLY` throughout this phase's parity matrices and device-test reports — never claimed as tested. Carried forward from the original migration's R9. |
| R18 | `bundleRelease`'s `signReleaseBundle` task and output filename (`app-release.aab`, no `-unsigned` suffix, unlike the APK path) could be misread as "signed" | **Verified via `jarsigner -verify`**: both products' AABs report "jar is unsigned." Documented explicitly in `retail-build-report.md`/`clinic-build-report.md`/`android-signing-guide.md` to prevent this exact misreading. |
| R19 | No client-side role-gated navigation exists for Clinic (Admin/Doctor/Secretary) despite being an expected workflow in Phase 4G's checklist | **Documented, not fixed**: grep-confirmed `clinic_role` is deserialized but never read by navigation code. Backend RBAC (`clinic_rbac_test.py`) is the real enforcement boundary. Building client-side role-gated nav would be a new feature, not a migration correction — out of this phase's scope by the addendum's own "do not redesign the products broadly" instruction. Recorded as a Wave 1 candidate. |
