## current accounts, roles and permissions

**1. Users table — yes, but it lives in `registry.db`, not `retail.db`.** `commercial_runtime/identity/registry_db.py:102-119`: `users(id, company_id, employee_id, email UNIQUE, password_hash, role DEFAULT 'employee', status DEFAULT 'active', require_password_change, session_version, language, clinic_role, failed_login_count, locked_until, created_at, UNIQUE(company_id, employee_id))`. Admin vs employee is real and account-level, not just device-level: `onboarding_routes.py:88-209` `create_admin()` is the only unauthenticated creation path (gated on "no valid admin row exists", `:120-125`), inserts `role='admin', employee_id='ADMIN-0001'` (`:142-146`). `onboarding_routes.py:369-427` `create_employee()` requires `session['mt_role']=='admin'` (`:371`), inserts `role='employee', status='pending_setup', password_hash='PENDING'`, auto-numbers `EMP-%04d` (`:392`), writes a 7-day single-use `secure_links` invite (`:405-411`) and returns `/#setup/<token>`; the invitee completes it at `employee_setup()` (`:632`). Also present: `update_status` (`:430`), `update_clinic_role` (`:448`), `update_perms` (`:479`), `get_employees` (`:354`) — all `mt_role=='admin'`-gated. **None of this is reachable from the retail UI**: `products/retail/frontend/app-shell.js:926` calls `/api/onboarding/create-admin` and nothing anywhere calls `/api/admin/employees` (no match in `products/retail/frontend/*` or `android/aura-retail/app/src/main/java`). Server-side it exists; product-side it is invisible.

**2. Login.** One endpoint for both platforms: `commercial_runtime/identity/auth_routes.py:24-55` → `mt_auth.authenticate_registry_user()` (`mt_auth.py:124-200`: case-insensitive email, hash upgrade, 5-strike/15-min lockout at `:33-34`, disabled-account reject) → `create_session()` (`mt_auth.py:109-121`) stuffing `mt_user_id/company_id/employee_id/mt_role/clinic_role/mt_session_version/require_password_change/email` into a **Flask signed cookie session** — server-side session store, no token, no JWT (`products/retail/backend/app.py:67-74`: `secret_key`, 12h lifetime, HttpOnly, SameSite=Lax). Desktop: same-origin fetch from `app-shell.js`. Android: `LoginScreen.kt:36` → `AuraApi.kt:18` `POST api/auth/login` over `http://127.0.0.1:<port>` against the **same Flask app embedded via Chaquopy** (`server/ServerBootstrap.kt:51-57,90`), with the cookie persisted to SharedPreferences (`net/ApiClient.kt:19-80`). `mt_login_required` (`mt_auth.py:203-230`) enforces only: demo bypass → `mt_user_id` present → re-read `users.status`, 401 if row missing or `disabled`; it **fails open on any DB exception** (`:226-227`) and **never checks `session_version`**, so the `session_version+1` bumps at `onboarding_routes.py:437,462,490` revoke nothing.

**3. Tenant model.** `company_id` is a TEXT string minted at first-run as `cfg['company_id'] or md5(admin_email)` (`onboarding_routes.py:138`) — per-install, never issued by Owner. Retail declares it `company_id INTEGER DEFAULT 1` on every table (`schema.py:1348,1357,1364,1386,1400,1410,1436,1478,1509,1534,1545,1553,1564`), while `_cid()` (`retail_api.py:75-76`) feeds it the registry's TEXT value — SQLite affinity tolerates it, but the declared type and the `DEFAULT 1` fallback disagree with what is actually stored. **Not company-scoped:** `sale_items` (`:1495`), `return_items` (`:1521`), `purchase_order_items` (`:1465`) — scoped via parent FK, defensible; `sync_outbox` (`:1577`), `sync_cursor` (`:1585`) — device-local by design; `user_permissions` and `user_devices` (`registry_db.py:122`, `device_registry.py:81`) — scoped only through `user_id`, so a cross-company `user_id` is enforced nowhere.

**4. Roles/permissions.** Two thin coexisting systems. (a) `users.role` ∈ {`admin`,`employee`} — a bare string, no role table, checked by literal `== 'admin'` comparisons. (b) `user_permissions(user_id, subsystem, access_level)` (`registry_db.py:122-129`) checked by `mt_require_subsystem` (`mt_auth.py:269-304`): admin bypasses entirely (`:287`), everyone else needs a row with `access_level != 'none'`. But **`subsystem` in retail is always the single literal `'retail'`** — every one of the ~80 decorated routes uses `@mt_require_subsystem('retail')` (`retail_api.py:200,320,334,359,…`). So the permission grid has exactly one cell: you have retail, or you don't. There is no per-capability retail permission — no "may void", "may discount", "may see reports", "may adjust stock". `require_clinic_role` (`mt_auth.py:233-266`) is clinic-only. `RETAIL_RESTRICTED_ALLOWLIST` (`retail_api.py:64-72`) is a *licensing* degradation list, not a user-role one. Net: retail has **admin vs everyone, and nothing finer**.

**5. User ↔ device.** Structurally decoupled, and the coupling that was scaffolded is dead. `devices` + `user_devices` exist (`device_registry.py:50-88`) with a DB-enforced one-admin-device-per-company partial index (`:65-66`), and the module's own docstring says "an account existing does not by itself authorize login from every device" (`:18-20`). But `grant_user_device` (`:273`) and `user_device_is_authorized` (`:297-304`) have **zero production callers** (only tests) — login never consults `user_devices`. So today: any user may log in from any device, unlimited users per device, unlimited devices per user, bounded only by licence slots. `_is_admin_device()` (`retail_api.py:169-177`) gates the audit-log route on *device* admin-ness, orthogonal to `mt_role`. Worse for the stated goal: each install has its **own `registry.db`** (`registry_db.py:29-31`; Android `filesDir` at `ServerBootstrap.kt:51`), so the admin's desktop account and the admin's phone account are two unrelated rows that merely happen to share an email. Accounts do not sync — `sync_outbox` carries only category/product/customer/supplier/reorder.

**6. Branches.** `branches(id, company_id, name, address, phone, status)` (`schema.py:1346-1354`), auto-healed to a single "Main Branch" on demand (`retail_api.py:94-106`). **Neither a user nor a device is bound to a branch** — no `branch_id` on `users`, `devices`, or in the session. Every device silently operates on `_default_branch()` = the company's first branch. Attribution is free text throughout: `sales.cashier TEXT DEFAULT 'POS'` (`schema.py:1482`), `returns.cashier` (`:1513`), `inventory_movements.created_by TEXT DEFAULT 'System'` (`:1394`), `cash_sessions.opened_by/closed_by` (`:1198,1201`), `held_sales.held_by` (`:1314`) — **no FK to `users.id` anywhere in retail.db.**

**7. Owner CC.** It has the real thing: `owner/app/models/staff.py` — `owner_roles:15`, `owner_permissions:26`, `owner_role_permissions:34`, `owner_staff_users:47`, `owner_staff_role_assignments:83`, `owner_staff_sessions:99`, `owner_staff_invitations:124`, `owner_mfa_credentials:151`, `owner_mfa_recovery_codes:168`, `owner_login_attempts:180`. It is a **separate world**: PostgreSQL, `owner_`-prefixed, and it models *Aura's own back-office staff*, not a merchant's cashiers. Retail reaches Owner only for licensing assertions and the sync relay (`commercial_runtime/licensing_contracts/*`, `owner/app/sync/routes.py`); no route, model, or table crosses over. Reusable as a **design template** (permission codes, invitation flow, session-version revocation, MFA are all solved once already), not as a runtime dependency — unless a deliberate decision is made to promote Owner into the merchant-identity authority, which today it is not.

---

**Blunt assessment.** You are closer than the roadmap implies on *account plumbing* and nowhere at all on the thing the product owner actually asked for. The admin/employee distinction, password hashing with lockout, invite-token onboarding, an admin-only employee CRUD surface, and a per-subsystem permission table are all written and tested — that is maybe 60% of a conventional user-management backend, and it should be built on, not rewritten. What is missing is everything that makes it *a retail system's* user model: the permission vocabulary has exactly one word (`'retail'`), so "employee" and "admin" differ only in whether they can reach `/api/admin/*`; no sale, return, stock movement or cash session carries a `user_id` FK, only a free-text `cashier` string, so you cannot answer "who voided this" or "whose till is short" no matter what accounts you create; no user or device is bound to a branch; and the admin-only surface has no UI on either platform, so from the customer's seat the feature does not exist. And the headline requirement — "the admin sees the same data on desktop and phone" — is not a user-account problem at all: `registry.db` is per-install, so the two admin accounts are unrelated rows, and even if you unified them, sales/returns/inventory/PO/cash are excluded from the sync manifest by design, which is the original complaint restated. Honest split: identity is an *extension* job (add a role/permission table, add `user_id` FKs, add `branch_id` binding, expose the existing admin routes in the UI, actually wire the dormant `user_devices` check and the ignored `session_version`); making one admin identity span two devices with matching data is a *from-nothing* job that requires promoting account identity to a synced, Owner-issued entity and extending replication to the transactional tables — and that second half lands squarely on the three known replication gaps you already documented (no conflict rule, no tombstones, full-row-snapshot updates), which are precisely the things that turn a shared ledger into silent data loss. Sequence the identity extension first; do not let it imply the sync half is nearly done.

## sync scope and what widening it costs

**1. What syncs today — 5 entity types: `category, product, customer, supplier, reorder_request`**
- *Declared*: `commercial_runtime/sync/sync_service.py:8-15` (docstring); *enforced as a literal tuple twice*: `:292` (company_id prefetch) and `:326` (`_apply_event` guard — unknown types silently `return`, never error). Apply branches `:330-422`.
- *Client enqueue*: `retail_api.py:87` `_queue_sync_event`; call sites `:350,374,404` (category) `:498,557,575` (product) `:752,780,798` (customer) `:862,904,922` (supplier) `:1459,1501` (reorder_request); duplicate helper `import_api.py:1086` (sites `:1134,1165,1183,1359,1367,1392,1435`); `core/retail/reorder_hook.py:202`. That set of call sites *is* the enqueue allowlist — there is no list constant.
- *Server relay*: **no entity allowlist at all**. `owner/app/sync/routes.py:175` only bounds `entity_type` to 1-64 chars (`:59`). The real gate is `:168` `entity_id = uuid.UUID(str(raw["entity_id"]))` → any non-UUID id raises `InvalidEventError`, and `:338-340` rolls back the **whole batch** with `INVALID_EVENT`. `SyncEvent.entity_id` is a Postgres `UUID` column (`owner/app/models/sync.py:33`). Android's `commercial_runtime/sync/internal_routes.py` and `SyncCoordinator.kt` forward raw batches — no entity logic anywhere.

**3.** Genuinely append-only → merge with no conflict rule: `inventory_movements`, `sale_items`, `return_items`, `cash_movements`, and the `sales`/`returns` headers. Mutable, need a rule: `inventory_balances` (or drop it — see 4), `purchase_orders`+items, `cash_sessions` (its one-open-per-branch partial unique index becomes a genuine cross-device conflict: two devices each legitimately open a session for branch 1).

**4. inventory_balances is derivable.** `stock_reconciliation.py:16-17` states the contract; `_DRIFT_SQL:88` is literally `SUM(quantity) GROUP BY product_id, branch_id`, and `repair_drift:176-180` overwrites the cache with that sum. All writers already store signed quantities (`:19-25`). Nothing lives only in the balance row except `quantity_reserved` (`schema.py:1404`) — which no code path ever writes, so it is dead at 0. **The blocker is not the balance, it's `branch_id`**: `branches.id` is `INTEGER AUTOINCREMENT` (`schema.py:1346-1347`) minted locally by `_default_branch` (`retail_api.py:100-106`), so device A's branch 1 and device B's branch 1 are unrelated rows. A merged ledger sums correctly only once branches are a synced entity with globally-unique ids. Second caveat: `_seed_retail` writes balances with no opening movement (`stock_reconciliation.py:43-48`).

**5. ID scheme / collision.** New sales, returns, movements, items, POs all take `cur.lastrowid`. Two offline devices both mint `sales.id=101`, and each computes `sale_number` from its **own** `doc_sequences` counter (`retail_api.py:2956-2961`, `:1693`) — so both also produce `SALE-000101-<cid>`. On merge that is a PK collision *and* a UNIQUE violation on `sale_number`; under all-or-nothing apply the receiving cursor never advances and that license's entire sync jams — the exact failure `retail_api.py:1394-1404` cites as why POs are excluded. Today it can't even reach the wire: `routes.py:168` rejects the non-UUID `entity_id` first. **The established pattern is `_migrate_products_to_uuid`, `schema.py:528-660`** (v3→v4): `PRAGMA foreign_keys=OFF` + explicit `BEGIN`; build `products_new` with `id TEXT PRIMARY KEY`; `id_map = {old: str(uuid.uuid4())}`; `DROP products` + `RENAME` (never rename the original away, `:470-473`, or SQLite silently rewrites children's FK text); then rebuild all five FK children from the `referencing` list `:594-626` remapping `product_id` through `id_map`. Same shape at `:296-311` (categories), `:715` (customers), `:805` (suppliers). `reorder_requests` was born with UUIDs; `cash_sessions`/`cash_movements` already are.

**6. Volume.** ~500 sales/day × ~4 lines ≈ 500 sale + 2,000 sale_item + 2,000 movement + ~50 return/return_item events ≈ **4,500-5,000 events/day/device**, vs. tens today. Transport carries it comfortably: push chunks of 200 (`sync_service.py:75`, `SyncCoordinator.kt:82`) against Owner's `_MAX_PUSH_BATCH=200` (`routes.py:57`, `:324`), pull `limit(500)` (`routes.py:394`) on a 10s tick (`sync_service.py:146`, `:549`) = 3,000 events/min inbound ceiling, so a full day drains in ~2 min; a day offline is ~25 push round-trips. The unaddressed cost is **server-side retention**: `owner_sync_events` has no TTL, no pruning, no `DELETE` anywhere in `routes.py`/`models/sync.py`, and each event carries a full-row JSONB snapshot — 5k rows/day/license grows without bound. Pruning below the slowest device's cursor is the missing piece, not throughput.

**7. Both devices sell the last unit offline.** Today: neither event exists to relay. Each device appends its own `sale_out` movement (`retail_api.py:1712-1715`) and decrements its own cache (`:1717-1719`); each shows stock 0 while the shop is actually at −1. Nothing ever detects it — the two databases simply diverge, permanently and silently, which is the reported complaint. Ledger-derived: both movements are append-only rows with distinct UUIDs, so they merge with **no conflict resolution needed**; the recomputed sum is −1, `compute_drift` (`stock_reconciliation.py:99`) surfaces it, and it is attributable to a device and a timestamp. The oversell still happened — offline can't prevent it without reservations — but it becomes a visible, reconcilable exception instead of invisible divergence.

## stock, cash and reporting data flow

**1. inventory_movements / inventory_balances writers** — five paired writers, each in one txn on one connection: `create_product` retail_api.py:488(bal)/493(mov, only if `initial_stock>0`); `adjust_stock` :684/:688 (BEGIN IMMEDIATE :642); `receive_purchase_order` :1215/:1219 (:1197); `create_sale` :1712(mov)/:1716(bal) (:1568); `create_return` :2222/:2230 (:2128); `_handle_retail_products` import_api.py:1313/:1317 (delta-gated). **Unpaired:** `stock_reconciliation.repair_drift`:171-180 writes balance only (by design); `_seed_retail` schema.py:1726,1730 inserts balances with **no** opening movement, then schema.py:1799 inserts `sale_out` movements with **no** balance decrement — seed drifts in both directions; import_api.py:1276 creates a zero balance row with no movement (harmless).

**2. stock_reconciliation** — recomputes `SUM(inventory_movements.quantity)` per `(company_id, product_id, branch_id)` and compares to the stored `quantity_on_hand`; tolerance `DEFAULT_TOLERANCE = 0.0005` (:58); full-outer-join emulation so movement-only and balance-only keys both surface (:80-92). As the post-merge derivation *rule* it is right and already the codebase's stated contract. As the merge *mechanism* it is not fit yet: `inventory_movements.id` is local `AUTOINCREMENT` (schema.py:1385) with no per-device natural key, so a movement replayed twice becomes two ledger rows and repair bakes the double in as "truth"; it skips `branch_id IS NULL` rows entirely (`repairable` :139); it is a whole-company full recompute with no seq/watermark, so it cannot run incrementally per applied batch; and it manages no transaction of its own (:153) — the caller must hold BEGIN IMMEDIATE, which a background sync thread currently does not.

**3. Cash** — terminal-bound facts: `opening_float`, `closing_float_counted`, `variance`, and every `cash_movements` row (float_in/out, paid_in/out — schema.py:1220-1229); these describe one physical drawer. Company-level: the `sales`/`returns`/`payments` rows themselves and all revenue/COGS/stock derived from them. **The bug for a synced world is that the session is keyed to a BRANCH, not a terminal**: `cash_sessions(company_id, branch_id, …)` schema.py:1194 with `idx_cash_sessions_one_open_per_branch` UNIQUE `WHERE status='open'` (schema.py:1213-1215), and `_open_cash_session_id` retail_api.py:108-131 stamps whichever session is open for that branch onto every sale (:1581) and return (:2133). Two devices on one branch therefore share one drawer session and `_cash_session_report` (:2339-2351) folds phone takings into the desktop's Z report. A terminal/device column on `cash_sessions` plus a per-(company,terminal) unique index is the minimal correct change.

**4. Branches** — stock is per branch: `inventory_balances.branch_id INTEGER NOT NULL`, `UNIQUE(company_id,product_id,branch_id)` schema.py:1402,1405; `inventory_movements.branch_id` is nullable (:1388). Sales carry `sales.branch_id` (:1480, nullable), returns `:1512`, POs `:1440`, reorder_requests `branch_id`. **Devices are not bound to a branch**: `devices` (device_registry.py:50-66) has company/fingerprint/`is_admin_device` only. Branch resolves per-request from the body else `_default_branch` retail_api.py:94-106 = lowest branch id, self-creating "Main Branch". And `branches.id` is `AUTOINCREMENT` (schema.py:1347) while `branch` is *not* a synced entity (sync_service.py:326) — desktop branch 1 and phone branch 1 are unrelated rows sharing a key, which silently makes the whole `inventory_balances` primary key non-portable.

**5. metrics.py** — the aggregation shape is multi-device-safe: every figure is a SUM/COUNT under one `_scope` predicate (`company_id` + `date(created_at)` range + optional `branch_id`, :265-276), no id arithmetic, no ordering dependence, and buckets are the union of sale and refund keys. Four single-device assumptions: (a) `date(created_at)` / `strftime('%H',created_at)` (:498, :510) read a **local wall-clock** string written by whichever device rang the sale (retail_api.py:1572, :2206) — clock skew or a phone in another timezone files rows on the wrong day/hour; (b) `_bucketed(..., 'branch_id')` and `revenue_by_branch` :646 key on the local integer branch id (see 4); (c) `inventory_value` :421 reads the balance **cache**, not the ledger, so it is wrong for the whole interval between a merge and a reconcile; (d) `transactions` = `COUNT(*)` over `sales` is correct only if the merge never duplicates a sale row — and `sales` has no cross-device key except nullable `idempotency_key` (schema.py:1491).

**6. Purchase orders** — contendable state: `purchase_orders.status` pending→received is a single global flip protected only by a *local* `BEGIN IMMEDIATE` + `AND status<>'received'` (retail_api.py:1225-1230); `purchase_order_items.received_qty` is SET to the full ordered quantity (:1223) — there is no partial-receipt model, so two devices receiving one delivery is a doubled `purchase_in`, not a split; `po_number` is bare-UNIQUE (schema.py:1438) but minted from a per-device counter (`_next_ref` :2956-2961); `split_group_id/routing_status/routed_at/routed_to/idempotency_key` (schema.py:1455-1462) are unowned workflow state. Worst case is `reorder_requests.status`: it **is** synced and applied as a blind last-writer-wins upsert (sync_service.py:414-421), while accepting also drafts a deliberately-unsynced local PO (retail_api.py:1436-1449) and the duplicate guard only reads the local table (reorder_hook.py:117-120) — accept on desktop + accept on phone yields two POs for one shortage.

**7. Local ids / sequences / device clock** — `AUTOINCREMENT` PKs on every transactional table (`branches` 1347, `inventory_movements` 1385, `inventory_balances` 1399, `purchase_orders` 1436, `purchase_order_items` 1466, `sales` 1477, `sale_items` 1496, `returns` 1508, `return_items` 1522, `payments` 1532, `journal_entries` 1552, `audit_log` 1563), consumed via `cur.lastrowid` (retail_api.py:106, 1127, 1704, 2215). Only categories/products/customers/suppliers/reorder_requests/supplier_contacts/cash_sessions/cash_movements are UUID — which is exactly why the Owner relay 400-rejects a whole push batch on a non-UUID `entity_id` (documented retail_api.py:1392-1399). `_next_ref` (:2956) increments a **per-device** `doc_sequences` row, so both devices mint `SALE-000001-<cid8>`/`RET-000001`/`PO-000001` against bare-UNIQUE columns (schema.py:1438,1479,1510). `sync_cursor` is a single local row (schema.py:1585). Clock: `sales.created_at`, `returns.created_at`, `_now()` (:2951) for cash sessions/movements, and PO `ordered_at`/`received_at` (:1227) are all `datetime.now()` **local**, while `sync_outbox.created_at` is UTC ISO (:91) — so ordering across the two clocks is not comparable, and every report predicate sits on the local-clock column.

## how real retail systems solve this

**1. OFFLINE-FIRST POS — local-first capture, deferred settlement, deliberately shrunken feature set**
- Square: device queues encrypted card payments locally, auto-processes on reconnect; must reconnect within 24h (hard expiry 72h); per-txn limit defaults to $100, configurable up to $50k; merchant bears declines/chargebacks on offline payments. ([Square offline mode](https://squareup.com/help/us/en/article/7777-process-card-payments-with-offline-mode), [press](https://squareup.com/us/en/press/square-brings-offline-payments))
- Shopify POS: offline = cash + manual payment types only. **Blocked offline**: creating products/customers, gift cards, returns, exchanges, voids, discount codes, tips. Orders and inventory do not sync until reconnect. ([Shopify offline features](https://help.shopify.com/en/manual/sell-in-person/shopify-pos/selling-offline/offline-features))
- Lightspeed X-Series: offline impossible without a completed initial sync AND an already-logged-in session; offline restricted to Sell/Status pages, cash only. ([Lightspeed](https://x-series-support.lightspeedhq.com/hc/en-us/articles/25534272395163-Selling-in-offline-mode))
- Odoo POS: cannot *open* a new session offline; an open session preloads catalogue into IndexedDB + Service Worker and queues unsynced orders. ([Odoo forum](https://www.odoo.com/forum/help-1/what-s-the-mechanism-of-pos-offline-283217))
- **The pattern**: preloaded read cache of catalogue → sale written locally as the authority with a client-generated id → queue-and-forward with server-side dedup → *narrow the offline surface to operations that are safe to replay blindly*. Returns/voids/gift cards are excluded everywhere because they need authoritative server state. This is the single most transferable decision.

**2. INVENTORY — ledger, not balance; oversell is allowed and reconciled**
- Square's Inventory API is explicitly append-only: `InventoryChange` of type `ADJUSTMENT` / `PHYSICAL_COUNT` / `TRANSFER`; `InventoryCount` is documented as a Square-*estimated* quantity derived by summing adjustments since the last `PHYSICAL_COUNT`. Ledger = truth, balance = derived view — identical to your `stock_reconciliation.py`. ([Inventory API](https://developer.squareup.com/docs/inventory-api/how-it-works), [InventoryCount](https://developer.squareup.com/reference/square/objects/InventoryCount))
- `PHYSICAL_COUNT` is the ledger's **checkpoint/truncation point** — it resets the computed quantity to an observed one. Square warns it must be a real count, never arithmetic. Adopt this: a stocktake is an event, not an UPDATE.
- Changes carry client RFC 3339 timestamps and **may arrive out of order**; Square sorts by timestamp, so a late offline sale timestamped before a physical count is applied *before* it, preserving count accuracy.
- Two terminals selling the last unit offline: **no product prevents it.** Shopify documents temporary overselling as an expected outcome of offline/multi-channel concurrency. Loyverse instead *hides* stock levels and negative-stock alerts entirely while offline. Square lets the derived count go negative and reconciles.
- **Accepted trade-off**: a refused sale is worse than an oversell. Oversell is treated as a *business* exception (backorder, substitute, refund), not data corruption. Hard reservations only exist when online. Do not build distributed locking for stock.

**3. IDENTITY — one owner account, permission sets, PIN ≠ password**
- Square: owner/account holder, then permission sets at three levels (Standard/Enhanced/Full) covering POS actions, cash drawer, discounts, refunds, reports, timecards, settings. Free tier forces one shared set per location; paid tier allows per-member-per-location sets. ([permission sets](https://squareup.com/help/us/en/article/5822-employee-permissions))
- Square passcode types map directly onto the identity question: **Owner passcode** (full access + sensitive data), **Team passcode** (shared, explicitly *no* per-person tracking of time/sales/activity), **Personal passcode** (unique 4-digit, enables per-member attribution of sales, time and actions). Loyverse requires a unique 4-digit PIN for every user including the owner. ([Square passcodes](https://squareup.com/help/us/en/article/8357-require-passcodes-at-point-of-sale), [Loyverse PIN](https://help.loyverse.com/help/pin-code-access))
- **Why PIN vs password**: the email/password is the *account* credential (enrolls devices, opens back office); the PIN is a fast **attribution switch** on an already-authenticated terminal. A 4-digit PIN is not a security boundary against someone holding the device — it's accountability between coworkers at a shared till. Consequence: never let a PIN alone authorize destructive or back-office actions (voids of closed sales, price/cost edits, employee management, license changes) — require owner passcode or password.
- Minimum role set observed across all five: Owner/Admin → Manager (refunds, discounts, reports, stocktakes, close drawer) → Cashier (sell, cash in/out, own-shift totals only). Anything more granular should be a permission set, not a new role.

**4. DEVICE vs USER — orthogonal, and both belong on every record**
- Square **device codes** pair a *device* to a *location* for device-level reporting, explicitly so employees never receive the account email/password; team members then sign in on top with passcodes. ([device codes](https://squareup.com/help/us/en/article/8339-set-up-device-codes))
- Standard model: **terminal registration** (licensed, bound to merchant + location, revocable from back office, survives staff turnover) ⟂ **user session** (per-shift login, roams between terminals). Every transaction record carries *both* originating device id and acting user id — device for reconciliation/drawer/licensing, user for accountability.
- Your `commercial_runtime/identity/` device-admin is the **device axis only**; it is not a substitute for the user axis and the two must not be collapsed. "Admin sees same data on desktop and phone" is a statement about the *user* axis (one merchant account, two registered devices), not about device admin.

**5. CASH DRAWER — bound to the terminal, not the user; the session is the auditable unit**
- Square's Cash Drawer Shifts API: a shift tracks cash "for a particular device, in a particular location", with `opened_at`/`ended_at`/`closed_at`, `opened_cash_money`/`expected_cash_money`/`closed_cash_money`, and states `OPENED` → `ENDED` → `CLOSED`. Lightspeed does cash management per *register*. ([Cash Drawers API](https://developer.squareup.com/reference/square/cash-drawers-api), [shift states](https://developer.squareup.com/reference/square/enums/CashDrawerShiftState))
- Multiple employees transact into one drawer shift; per-employee accountability comes from personal-passcode attribution on each transaction, **not** from the drawer. Don't bind a drawer session to a user.
- The `ENDED` vs `CLOSED` split is deliberate and worth copying: *counting* the drawer and *approving* the variance are distinct acts by distinct people — which is exactly the AUDIT-032 self-approval property you just implemented.

**6. SYNC CONFLICTS — server-authoritative with optimistic concurrency; the window is closed by policy, not by algorithm**
- Square catalog objects carry a monotonically increasing `version`; an update sent with a stale version is rejected with `VERSION_MISMATCH` and the client must re-read and re-apply. Not LWW, not merge — **reject and refetch**. ([optimistic concurrency](https://developer.squareup.com/docs/build-basics/common-api-patterns/optimistic-concurrency))
- Crucially, these products mostly *avoid* the conflict rather than resolve it: Shopify POS cannot create or edit products offline at all; Lightspeed allows offline product *creation* (a create, not a contended update). Catalogue editing is effectively an online, back-office activity.
- **The public record is thin on field-level merge**: I found no evidence that Square, Shopify, Lightspeed, Loyverse or Odoo document per-field/CRDT merge for catalogue data, and none of them tell merchants a conflict-resolution rule in user-facing docs. Treat "server-authoritative + version check + reject" as the defensible answer; your current blind full-row upsert is the thing with no precedent.
- Direct implication for your replication gaps: catalogue (category/product/customer/supplier) → server-authoritative, row version, reject-on-stale, soft-delete tombstones. Transactional data (sales/movements/cash) → append-only immutable events where conflict is structurally impossible. Two different policies, not one.

**7. FAILURE MODES WITH RECEIPTS**
- **Offline order loss**: Shopify explicitly warns that logging out of POS or powering off the device *can lose offline orders*. Persist on write to durable storage, never hold the queue in memory, and block logout while an unsynced queue exists.
- **Receipt numbering**: Shopify renders offline orders as register-prefix + receipt number (`#1-1005`, `#2-1013`). Per-device prefix + local monotonic sequence is the standard collision-avoidance mechanism. Never allocate a global sequential document number offline.
- **Clock skew**: Square orders inventory changes by *client-supplied* timestamp, which means a wrong device clock silently corrupts ledger ordering. Carry both device timestamp and server receipt sequence; order by server seq (you already have per-license append-only seq), keep device time for display/audit, and record the observed skew at sync so a bad clock is detectable.
- **Duplicate receipts**: client-generated UUID/idempotency key per sale, deduped server-side (Square requires one on `BatchChangeInventory`). You already have per-id idempotent push — extend the same discipline to sale documents.
- **Stale offline windows**: Square's 24h soft / 72h hard expiry is the pattern. Expire the offline window and degrade loudly; don't let a terminal drift for days accumulating unsettleable work.
- **Orphaned drawer sessions**: the OPENED/ENDED/CLOSED lifecycle exists because drawers get abandoned. Force-close a session that crosses a business-date boundary and flag it as an unverified variance rather than silently rolling it forward.
- **Honest-degradation lesson from Loyverse**: it hides stock levels and negative-stock alerts offline rather than display a cached number. Showing a confidently wrong on-hand figure is worse than showing none — directly relevant to the "stock is not accurate" complaint that started this work.
