# Phase 7 -- Product Trust Bootstrap Design (ADR-7.2)

## Decision

Chosen model (least complex of Part D's three, cryptographically sound for this project's actual scale): **application-upgrade-delivered trusted keys, with a signed key-set manifest for in-place rotation between upgrades.**

## Why not the other two options

- *Offline root key signing online-key manifests*: correct for a large public PKI with independent root-key custody ceremonies. Aura Owner is a single internal service with one operator; introducing a second, colder root key and a signing ceremony process for it is real infrastructure this phase has no mandate to build (out of scope: no Aura Core integration, no production secrets-manager yet -- Phase 6's residual risk register already flags the manual signing-key runbook as future work, not solved here).
- *TOFU (trust-on-first-use)*: explicitly forbidden by Part D item 6.

## What Phase 6 already provides, and the one extension needed

Phase 6's `GET /api/licensing/v1/signing-keys` (`server-signing-key-management.md`, `export_public_keys()`) returns every published key (`ACTIVE` + `RETIRED`, never `REVOKED`) with `key_id`, `algorithm`, `status`, `created_at`, `retired_at`. This is *discovery*, not *trust* -- Part D item 9 forbids trusting a key merely because this endpoint lists it as active. The smallest compatible extension (per Part D's explicit permission to add "the smallest compatible Owner extension necessary" without redesigning Phase 6): the existing endpoint's response is wrapped in a **signed key-set manifest envelope**, signed by whichever key is the product's current *trust anchor* (the one bundled at build time, or the most recently trust-anchor-promoted key from a prior manifest). Concretely:

```json
{
  "manifest_version": 1,
  "issued_at": "...",
  "keys": [ /* existing signing-keys response, unchanged shape */ ],
  "signed_by_key_id": "<the anchor key's id>",
  "signature": "<base64, canonical(keys + issued_at + manifest_version)>"
}
```

This reuses `canonical.py` and `signing.py` verbatim -- the same primitive that already signs assertions now also signs the key-set manifest, keyed by whichever key the product currently trusts. Owner-side change: `owner/app/licensing_service/signing.py::export_public_keys()` gains a manifest-signing wrapper; `owner/app/api_external/routes.py`'s `/signing-keys` route signs its own response before returning. This is additive to Phase 6, not a redesign of it, and will be implemented as a small, separately-tested Owner-side change at the start of Phase 7 Part D implementation (tracked in `phase7-implementation-plan.md`), not silently bundled into product code.

## Bootstrap sequence

1. **Initial trust anchor**: each rc.2 build embeds the Owner signing key(s) `ACTIVE` at build time, as raw base64 public keys plus `key_id` plus algorithm, in a read-only bundled resource (`commercial_runtime/licensing_contracts/trust_anchor.json` on Windows/Android-Python side; mirrored into Android's `assets/` via the existing `stageAuraAssets` pipeline so Kotlin can also read it directly for its own advisory check). Generated by a build-time script that calls Owner's (now-signed) `/signing-keys` endpoint against the specific Owner instance this build is being cut for, and commits the result into the build -- never fetched at first-run over an unauthenticated channel.
2. **Every assertion verification**: the verifier only trusts a `signing_key_id` present in the *locally stored* trusted-key set (bundled anchor, unioned with any keys admitted via step 3). An assertion signed by a `key_id` outside that set is rejected (`UNKNOWN_SIGNING_KEY`), full stop -- never fetched-and-trusted on demand.
3. **Rotation overlap**: on every successful check-in, the product also fetches the signed key-set manifest. If the manifest's own `signed_by_key_id` is already in the local trusted set (i.e., signed by a key the product already trusts), and the manifest's signature verifies, every key it lists with status `ACTIVE` or `RETIRED` is admitted into the local trusted set (a `REVOKED` key already in the local set is removed). A manifest signed by an untrusted key, or with a bad signature, is discarded silently -- it never partially updates the trusted set.
4. **Revocation propagation**: same channel as rotation (step 3) -- a key that moves to `REVOKED` on Owner's side stops being trusted by every product on its next successful check-in. Between check-ins, an already-locally-trusted-but-now-revoked key can still verify old assertions until the local grace/offline window ends; this is bounded by the same offline-grace policy as everything else, not a separate exposure window.
5. **Unknown-key behavior**: reject the specific assertion or manifest; never fall back to "trust everything" or disable verification.
6. **Rollback behavior**: if a device is restored from an old backup/snapshot with a stale trusted-key set that no longer includes Owner's current active key, check-in fails closed (`UNKNOWN_SIGNING_KEY` on the *next* assertion, since the old assertion itself is still verified against the keys valid when it was issued) -- the product falls back to its last-known-good local state under the existing offline-grace policy, not an immediate hard failure. A human-readable message distinguishes this from a real suspension/revocation (`CLOCK_REVIEW_REQUIRED`-adjacent code, not `SUSPENDED`).
7. **Application-upgrade behavior**: every rc upgrade ships a fresh `trust_anchor.json`, so even a product that has been offline long enough to lose all rotation overlap can recover trust simply by installing the next release -- this is the ultimate fallback the "application updates deliver the next trusted public keys" option (Part D's third listed model) provides, used here as the recovery path underneath the primary manifest-rotation mechanism rather than as the sole mechanism.

## Implementation status

Owner-side extension (`export_signed_keyset_manifest()` in `owner/app/licensing_service/signing.py`, wired into `GET /api/licensing/v1/signing-keys` in `owner/app/api_external/routes.py`) is implemented and tested (`owner/tests/test_phase7_keyset_manifest.py`, 7 tests) -- additive only, `schema_version`/`keys` unchanged from Phase 6, `manifest_version`/`issued_at`/`signed_by_key_id`/`signature` are new fields. Client-side `OwnerTrustStore` (`commercial_runtime/licensing_contracts/trust_store.py`), the build-time generator (`scripts/generate_trust_anchor.py`), and the bundled-anchor loader (`trust_anchor_loader.py`) are implemented and tested (23 tests total across the three). Not yet done: actually invoking the generator against a real running Owner instance to produce a committed `trust_anchor.json` for a real build (deferred to Part Z/AA release-cut time, when a real signing key exists to anchor against) and wiring `OwnerTrustStore`/`trust_anchor_loader` into each product's actual startup sequence (Part E/F).

## Explicitly not done

No TLS-pinning scheme beyond standard OS/platform certificate validation (Part H governs transport trust; this document governs *application-layer* payload trust, which is intentionally independent of and additional to TLS, not a replacement for it).
