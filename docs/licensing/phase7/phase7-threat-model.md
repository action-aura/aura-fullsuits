# Phase 7 -- Threat Model

## Assets

Device private keys (Windows DPAPI blob, Android Keystore-wrapped blob). Local license state (SQLite rows). The bundled trust anchor. Customer business/medical data (must remain unreachable by any threat against the licensing subsystem, not just "not currently sent" -- see `product-to-owner-data-boundary.md`).

## Threats and mitigations

| Threat | Mitigation | Where |
|---|---|---|
| Attacker crafts a fake "licensed" response to a product that never talks to Owner | Every assertion independently signature-verified against the locally-trusted key set; no code path accepts an unsigned or unverified success | `AssertionVerifier`, Part K |
| Attacker replays a captured legitimate Owner response later, after suspension/revocation | Assertion `expires_at` bounds replay window; check-in cadence refreshes it; a replayed old assertion eventually expires under normal offline-grace evaluation, same as genuine offline use -- no special-cased "replay" state needed beyond what expiry already provides | `offline-enforcement-policy.md` |
| Attacker extracts the device private key from disk | DPAPI (Windows, user-scope) / Keystore-wrapped AES-GCM (Android) -- key never at rest in plaintext | `windows-device-key-storage-design.md`, `android-device-key-storage-design.md` |
| Attacker calls a product's mutation API directly, bypassing the UI | Capability guard enforced at the Flask route/service layer, not the frontend; direct-route bypass tests required (Part T, Part AF) | `clinic-restriction-capability-matrix.md`, `retail-restriction-capability-matrix.md` |
| Attacker sets the system clock back to make an expired/suspended assertion look current | Trusted-time model (last-verified-server-time + monotonic delta) instead of raw wall clock; suspicious rollback forces `CLOCK_REVIEW_REQUIRED`, not a free pass | see Trusted Time section below |
| Attacker floods the check-in scheduler to drain battery/bandwidth (Android) or hammer Owner | `WorkManager` (Android) / interval-bound thread (Windows) with backoff+jitter, respecting `Retry-After`; this is a *product-side* rate-limit-respecting client, distinct from but complementary to Owner's own Phase 6 server-side rate limiting | Part L |
| A compromised/rooted device extracts the Kotlin-verified assertion and replays it to the embedded Python backend's internal sync endpoint without ever having a valid device key | Python's `AssertionVerifier` independently re-verifies the assertion's signature and its `device_key_fingerprint` field against Python's own record of the registered device key -- it does not trust that "Kotlin already checked it" | `product-integration-architecture.md`'s authority-boundary table |
| Malicious actor with local admin/root replaces the bundled trust-anchor file to point at their own key | Cannot be fully prevented against a fully-compromised local admin/root attacker (out of scope for any client-side licensing scheme -- the spec does not claim otherwise); mitigated to the extent practical by shipping the trust anchor inside the signed installer (Windows Authenticode, once signing is available -- currently honestly disclosed as unsigned per Wave 1B/1C) / signed APK (Android, real production keystore) so tampering invalidates the package signature | `product-trust-bootstrap-design.md` |
| `cryptography` is unavailable or has no working Chaquopy wheel for the Android ABI/Python-version combination in use | Real risk, not yet resolved -- flagged explicitly here rather than assumed away. If unresolved, the embedded Python backend's independent assertion re-verification (the second half of the "never trust a Kotlin boolean" design) cannot use `cryptography`'s Ed25519 verify. Fallback path if this risk materializes: a minimal pure-Python Ed25519 verification routine (well-understood, small, algorithmically simple to verify against RFC 8032 test vectors) vendored directly into `licensing_contracts`, used only for verification (never signing) on the Android Python side -- avoiding any Rust/OpenSSL native-wheel dependency entirely. This decision is made for real during Part F/K implementation, based on an actual Chaquopy build attempt, not speculated further here. |
| Owner is entirely unreachable for an extended period (real outage, not attacker-induced) | Distinguished from suspension/revocation; governed entirely by the signed offline-grace policy already in the last valid assertion; never immediately treated as invalid | `offline-enforcement-policy.md`, Part AD |
| A stale rc.1 install with no licensing state is upgraded and its existing data misread as corrupt | Explicit `LEGACY_UNACTIVATED`/migration-pending handling, never conflated with `LOCAL_STATE_CORRUPT` | Part Y, tracked in `phase7-implementation-plan.md` |

## Trusted time

`commercial_runtime/licensing_contracts/trusted_time.py`: stores, per installation, `last_verified_server_time` (from the most recent assertion's `issued_at`/response `server_timestamp`) paired with the local monotonic clock reading (`time.monotonic()` on Windows-Python, `SystemClock.elapsedRealtime()`-backed on Android) at the moment it was recorded. "Current trusted time" = `last_verified_server_time + (monotonic_now - monotonic_at_verification)`. This is immune to wall-clock changes entirely (monotonic clocks don't move backward or jump on NTP/DST/user changes) but does NOT survive a full reboot on some platforms' monotonic-clock semantics -- documented explicitly rather than assumed: Windows' `time.monotonic()` is suspend-aware and does not reset on reboot within a session but does reset process-to-process, so the paired wall-clock anchor is persisted to the state repository and re-anchored (not reset to "trust nothing") on every process start, re-validated against the *next* successful check-in.

**Rollback detection**: if local wall clock, at any observation, reads earlier than `last_verified_server_time` by more than `clock_rollback_tolerance_seconds` (from the current policy, default 5 minutes per Phase 6's seeded default), and this isn't explainable by a timezone/DST offset change (checked by comparing UTC-normalized values, not local-zone-naive ones), it's flagged suspicious. A single such event does not immediately assume malice -- `CLOCK_REVIEW_REQUIRED` is entered (matching Part N's "do not silently grant unlimited grace... enter a safe restricted/warning state"), and the very next successful online check-in clears it by re-anchoring trusted time from Owner's fresh `server_timestamp`. Repeated rollback events across multiple sessions escalate to logging a `CLOCK_REVIEW_REQUIRED` local event each time (Part W) but do not compound into a harsher state than what a single event already produces -- there is no "three strikes" punitive design, since Part N explicitly warns against treating ordinary clock corrections as fraud.

## What this threat model does not claim to solve

Full device compromise (rooted Android device, admin-level Windows malware) can defeat any client-side control -- this is inherent to all client-side licensing and is not a gap specific to this design. The mitigations above raise the cost of casual bypass and ensure the *server* (Owner) remains the authoritative source of truth that any tampered client eventually falls out of sync with (via check-in, via assertion expiry) rather than attempting to make client-side enforcement unbreakable, which is not a claim this phase or any future phase makes.
