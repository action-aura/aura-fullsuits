# Phase 7 -- Android Device Key Storage Design (ADR-7.1)

## The reliability problem this document resolves

Android Keystore's native support for Ed25519 signing keys arrived only in API 33 (Android 13), and even then is inconsistent across OEM keystore implementations (StrongBox support varies; some OEM TEEs still reject Ed25519 key generation with a runtime error not a capability query). This product's `minSdk` is 26, and the one physical device validated in Wave 1A is an Infinix X6528 on Android 13 -- right at the edge of native support, not comfortably above it. Requiring native Keystore-generated Ed25519 would make the feature silently unavailable or crash-prone on a meaningful slice of the real target range. Part F explicitly anticipates and permits this: "where direct generation of the Phase 6 device algorithm is not reliably supported by the actual minSdk/device environment, generate the required device key in application storage and encrypt it with a non-exportable Android Keystore key."

## Decision

1. **Ed25519 keypair generation and signing**: pure-JVM library, not platform-native crypto -- avoids the API-33 cliff and OEM inconsistency entirely by never depending on AndroidKeystore's own Ed25519 support. Implemented with Google Tink's raw "subtle" primitives (`com.google.crypto.tink.subtle.Ed25519Sign`/`Ed25519Verify` from `com.google.crypto.tink:tink-android:1.15.0`), which are RFC 8032-compliant and produce raw 32-byte public keys / raw 64-byte signatures with no Tink keyset/prefix framing -- deliberately chosen over Tink's higher-level keyset API for this reason, since a keyset-wrapped signature would not be directly verifiable by Owner's Python `cryptography` library. **Verified for real, not assumed from documentation**: `Ed25519CrossVerifyTest.kt`, run via `./gradlew :app:testDebugUnitTest`, proved both directions of interop against this repo's actual `.venv` (`cryptography==43.0.1`) -- a signature produced by Kotlin/Tink verified successfully with Python's `Ed25519PublicKey.verify()`, and a signature produced by Python's `Ed25519PrivateKey.sign()` verified successfully with Tink's `Ed25519Verify`. This is the strongest form of the cross-platform-compatibility claim: actual bytes, actual independent libraries, both directions.
2. **At-rest protection of the generated private key material**: AES-256-GCM, key generated inside Android Keystore (`KeyGenParameterSpec`, `setIsStrongBoxBacked(true)` where available with graceful fallback, non-exportable, hardware-backed where the device supports it) -- this part *does* use native Keystore, because AES-GCM key wrapping is universally supported back to API 23 and has none of Ed25519's rollout gaps. The Ed25519 private key bytes are the *plaintext* input to this AEAD; the Keystore-backed AES key never leaves the TEE/StrongBox and is never itself exportable. Implemented behind a `KeyWrapper` interface (`AndroidKeystoreWrapper` in production) rather than hardcoded directly into the device-identity class -- see "Testability finding" below for why.

## Testability finding: Robolectric does not provide a working AndroidKeyStore provider

First implementation attempt wired `KeyStore.getInstance("AndroidKeyStore")` directly into the device-identity class and used Robolectric (`org.robolectric:robolectric:4.13`) to run JVM-level tests against it. Every test touching the keystore failed with `KeyStoreException` wrapping `NoSuchAlgorithmException` -- Robolectric does not register a working `"AndroidKeyStore"` JCA security provider out of the box, a real, documented Robolectric limitation, not a bug in the device-identity code. Resolved by extracting the wrap/unwrap operation behind a `KeyWrapper` interface, with `AndroidKeystoreWrapper` as the real production implementation and a genuinely-AES-GCM (but non-Keystore-backed) `FakeKeyWrapper` injected in tests -- this tests `DeviceIdentity`'s own logic (generate/sign/corruption-detection/reset-flow/fingerprinting) for real on the JVM with no Robolectric dependency at all, while `AndroidKeystoreWrapper` itself is exercised only on a real device/emulator. Robolectric was removed from `build.gradle` after this refactor made it unnecessary -- not left in as unused dependency weight.
3. **Storage location**: app-private internal storage (`context.filesDir`, never external/shared storage, never `assets/`), file `licensing/device_key.enc` holding the AES-GCM ciphertext + nonce + auth tag. A companion `device_key_meta.json` mirrors the Windows-side safe-metadata-only convention (fingerprint, algorithm, created_at, installation state) -- never the key itself.

## Why this satisfies "device private key never leaves the device" and "non-exportable"

The Ed25519 private key exists in plaintext only transiently, in process memory, for the duration of a signing operation, reconstructed by AES-GCM-decrypting the on-disk blob using the non-exportable Keystore AES key -- which itself cannot be extracted from the device under normal OS operation (hardware-backed on devices with StrongBox/TEE support; software-backed Keystore fallback on devices without, still outside normal app-process memory-dump exposure via `android:allowBackup` and standard sandboxing). This is the same "generate in app storage, wrap with a non-exportable Keystore key" pattern Part F names explicitly, not an improvised alternative to it.

## Backup exclusion (Part F requirement)

`android:allowBackup="false"` is the simplest fully-correct answer, but the existing apps may already rely on `allowBackup` for legitimate product-data reasons -- this must be checked against the real current manifest during implementation, not assumed. If `allowBackup` must stay `true` for other reasons, the fallback is Android's `<data-extraction-rules>` (API 31+) / legacy `<full-backup-content>` (API 23-30) manifest mechanism to explicitly exclude the `licensing/` directory by path from both cloud auto-backup and device-transfer backup -- both paths are documented here so implementation picks whichever matches what the manifest actually does today.

## Corruption and reset

Mirrors `windows-device-key-storage-design.md`'s three-way split (missing -> `ACTIVATION_REQUIRED`; present-but-undecryptable -> `LOCAL_STATE_CORRUPT`, no silent regeneration; present-and-valid -> normal operation). AES-GCM's authentication tag makes "undecryptable" and "tampered" the same detectable failure mode, so no separate integrity check is layered on top.

## What is never done

No Android ID, IMEI, serial number, or MAC address is read or used as identity input (Part F's explicit reject list) -- identity is proof-of-possession over the generated Ed25519 key only. No key material in Logcat (verified by an explicit grep-based test over captured log output during Part AA validation, not just code review). No key material in the APK's `assets/` (only the *public* trust-anchor bundle from Part D lives there). No key material crosses the Kotlin-to-Python localhost boundary described in `product-integration-architecture.md` -- only signed request bodies and verified-in-place assertion responses do.
