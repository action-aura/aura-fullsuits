Status 2026-10-13 (JOFOTARA-1): the document builder and its validator are
complete and tested offline. Transport (`providers/direct_istd.py`) is still
`NotImplementedError`: it needs the owner's JoFotara Client-Id / Secret-Key /
activity number, and nothing in this repo has ever contacted ISTD.

Code: `commercial_runtime/einvoicing/istd_ubl.py` (builder + `validate_istd_document`),
helpers in `document.py` (type name, UUID, ICV, tax category), dispatch in
`ubl.render_document_xml`, Retail wiring in

## Rules implemented (ids appear in code and test docstrings)

| Rule | What | Source |
|------|------|--------|
| R-TYPE | `InvoiceTypeCode` 388 new / 381 return. `@name` = 3 digits: trade type (0 local), payment (1 cash, 2 receivable), tax family (1 income, 2 general sales, 3 special). A return repeats the original's `@name`. Mismatch with the taxpayer's registration is rejected by ISTD ("not authorized to submit this type of invoice"). | Q1 Q2 Q4 |
| R-UUID | `cbc:UUID` generated by the taxpayer system, stored before first send, reused on every retry. | Q3 Q4 |
| R-ICV | `AdditionalDocumentReference`: `cbc:ID`=`ICV`, counter in `cbc:UUID`, starts at 1. | Q1 Q4 |
| R-SELLER | `AccountingSupplierParty`: country JO, tax number in `CompanyID`, scheme VAT, registered name. `SellerSupplierParty/cbc:ID` = income-source (activity) sequence. | Q1 Q6 |
| R-BUYER | Identifier scheme mandatory (`TN`, `NIN`, `PN`), number optional/digits. Buyer name mandatory on receivable and on cash above JOD 10,000. | Q1 |
| R-LINE | Category `S` (rate>0), `Z` (exempt, 0), `O` (zero-rated, 0); `S` never with 0%. Accepted rates 0,1,2,3,4,5,7,8,10,16. Scheme `VAT` (`UN/ECE 5153`), category `UN/ECE 5305`, `schemeAgencyID` 6. No negative quantity or price. Unit `PCE`. | Q1 Q5 Q6 |
| R-TOTAL | No invoice-level discount (spread across lines). Header discount = sum of line discounts; header TaxTotal = sum of line tax; `TaxExclusive` = sum(qty x price); `TaxInclusive` = `Payable` = sum of line `RoundingAmount`. 3 dp, tolerance 0.001. | Q1 Q6 |
| R-INCOME | Income-family invoice (`@name` digit 3 = 1) carries no TaxTotal anywhere. | Q1 |
| R-RETURN | 381: `BillingReference/InvoiceDocumentReference` = original number + UUID, `DocumentDescription` = the ORIGINAL's total, `PaymentMeans` code 10 (`UN/ECE 4461`) + reason in `InstructionNote` (mandatory); buyer and currency as the original; no `Note`. | Q2 Q4 |
| R-MIN | Opening `<Invoice ...>` tag on one line ("Invalid Invoice Minification"). | Q1 |
| R-ENV | `cbc:ProfileID` = `reporting:1.0`; dates `yyyy-mm-dd`. | Q1 Q3 |

How this maps to our data (no schema change was allowed):

* UUID = uuid5 of (company, outbox `invoice_ref`): identical on every retry, nothing stored.
* ICV = the number minted by the dedicated `einvoice_sequence` (`INC-000042` -> 42). Credit notes draw from the SAME series, so the counter climbs across invoices and credit notes. The shop's local document number is never used (`phase1/invoice-numbering-audit.md`).
* `@name` is derived from payment type + `invoice_family` setting. A shop that charges general sales tax must set `invoice_family=general_sales`; the validator refuses an income-family document that carries tax (R-INCOME), because the default family is `income`.
* Tax category from `sale_items.tax_rate`: >0 -> S, 0 -> O.
* Selection: the ISTD profile is used when the `provider` setting is `direct_istd`, and always for credit notes. Every other install still renders the generic profile byte-for-byte as before.
* QR: ISTD RETURNS the QR (`EINV_QR`) and an accepted resend returns the original; the public texts describe no locally computed QR (the TLV format is the Saudi one, not Jordan's). So nothing is invented: `qr.qr_for_outbox_row` already prefers ISTD's own value.

Conformance: the golden documents validate against the official OASIS UBL 2.1
`Invoice` XSD (`xsdrt/`). That check is `tests/test_istd_xsd.py`; it needs `lxml`
and `AURA_UBL21_XSD_DIR` and otherwise SKIPS, because the XSD is not vendored
(its files are headed "All Rights Reserved" and redistribution terms were not
confirmed) and lxml is not a repo dependency. It was run once on 2026-10-13: 5 passed,
including a check that the schema rejects a mis-ordered document. XSD validity says
nothing about ISTD's own business rules, which are the table above.

## Open questions (public sources silent or contradictory -- NOT guessed)

1. **Z vs O.** The task brief and review B said "0% zero-rated -> Z, exempt -> O"; the guide as reported (Q5, p.42) says the opposite: `Z` = exempt, `O` = zero-rated (and export/free-zone must be `O`). Implemented per Q5, and kept as one function (`tax_category_for_rate`) so flipping is a one-line change plus the tests. UN/ECE 5305 itself defines Z as zero-rated and E as exempt, which is why this is worth confirming in the guide.
2. **Exempt goods cannot be expressed.** Retail has no per-product exempt flag and a schema change was out of scope, so every 0% line becomes `O`. An exempt product would be filed as zero-rated. Needs a product `tax_category` column (review B proposed schema v52) before JoFotara goes live for a shop selling exempt goods.
3. **Anonymous (B2C) buyer.** The scheme is mandatory but the number optional; the sources do not say which scheme an anonymous walk-in uses. We emit `schemeID="PN"` with an empty value. Confirm.
4. **Line-level discount element.** Q6 says line discounts exist but does not name the element. We put `AllowanceCharge` inside `cac:Price` (valid UBL). Confirm against a real example.
5. **Fourth namespace.** The guide says the root declares four; the public text names three. We add the UBL-standard `ext`.
6. **ICV scope.** Per taxpayer, per income-source sequence, or per document type? We use our per-company, per-series sequence (so two families = two counters), shared by invoices and credit notes.
7. **Credit-note numbering.** Same series as invoices (our choice) versus a separate return series: not stated.
8. **Return reason fallback.** The reason is mandatory; a till return typed with no reason files with the text "Goods returned". Confirm ISTD accepts a generic reason.
9. **Foreign currency.** The JOD 10,000 buyer-name threshold is enforced for JOD only; the foreign-equivalent rule and whether non-JOD `currencyID` is accepted (the guide's own examples print `JO`) are unknown. Samples in the public texts use `currencyID="JO"`; we emit the real ISO code `JOD`.
10. **Special sales tax (`@name` digit 3 = 3)** and export/free-zone trade types are not modelled.
11. **Partial-return rounding (pre-existing, recorded in ROADMAP UI-3a).** A credit note recomputes each returned line from the stored odd discount % like the refund does, so it can differ from the sale by 1-3 fils on cart-discounted lines. The credit note is internally consistent, but may not match the cash refunded to the fil.
12. **Sandbox.** Q2 states the guide does not say any test environment is open to taxpayers or developers; the first real submission may be the first real test.
