# Invoice numbering audit — JoFotara Phase 1

Governing wave: `docs/einvoicing/phase1/`. This doc exists to justify one
design decision before any e-invoicing code is written: **the ISTD-facing
invoice number is a new, separate, dedicated sequence — not a reuse of either
product's existing sale/invoice number.** Written before Part 2 of the
implementation plan (schema) so the schema can be reviewed against this
reasoning, not the other way around.

## Retail: `sales.sale_number`

Generated by `_next_ref()` (`products/retail/backend/api/retail_api.py:1185`):

```python
def _next_ref(conn, cid, doc_type):
    conn.execute("INSERT OR IGNORE INTO doc_sequences (company_id,doc_type,last_no) VALUES (?,?,0)", (cid, doc_type))
    conn.execute("UPDATE doc_sequences SET last_no=last_no+1 WHERE company_id=? AND doc_type=?", (cid, doc_type))
    n = conn.execute("SELECT last_no FROM doc_sequences WHERE company_id=? AND doc_type=?", (cid, doc_type)).fetchone()[0]
    return f"{_REF_PREFIX.get(doc_type, doc_type.upper())}-{int(n):06d}"
```

Called from `create_sale()` inside the `BEGIN IMMEDIATE` transaction opened
earlier in that function; every failure path rolls back, which rolls back the
`last_no` increment with it.

**Finding — sequential and gapless per company: yes.** The counter only
advances inside a transaction that either fully commits (sale + number
together) or fully rolls back (neither). No code path can consume a number
and abandon the sale.

**Finding — globally unique: no.** `sales.sale_number` carries a bare
`UNIQUE` constraint (`products/retail/backend/database/schema.py:189`):

```sql
sale_number TEXT UNIQUE,
```

`doc_sequences` counters reset per `company_id`. Company 2's first sale
generates `SALE-000001` — identical to company 1's — in the same shared
multi-tenant database. This is a live, unfixed bug, pre-existing and
unrelated to e-invoicing.

It is the *same* class of bug already found and fixed for `returns`
(`retail_api.py:972-980`):

```python
# returns.return_number carries a bare (not company-scoped) UNIQUE
# constraint, but _next_ref()'s counter resets per company -- two
# different companies' first return would otherwise both generate
# "RET-000001" and collide in this shared multi-tenant database.
# Appending a company fragment keeps the sequential part
# human-readable/searchable while guaranteeing global uniqueness
# without altering the shared _next_ref helper or its format for
# other doc types (out of scope for this correction).
ret_num = f"{_next_ref(conn, cid, 'return')}-{str(cid)[:8]}"
```

`sales.sale_number` never received the equivalent fix. `products/retail/tests/wave1c_financial_gate_test.py`'s header names this exact gap as a known, accepted "per-company doc_sequence reseed workaround for the bare-UNIQUE sale_number column" issue.

## Clinic: `clinic_invoices.invoice_number`

Generated in `create_invoice()` (`products/clinic/backend/api/clinic_api.py:770`):

```python
inv_no = f'INV-C-{int(time.time())}-{random.randint(100, 999)}'
```

**Finding — sequential: no.** Timestamp + random. Two invoices in the same
company have no ordering guarantee, no gaplessness, and no audit trail
suitable for a tax authority. There is no `doc_sequences`-equivalent table
for Clinic at all, and no `clinic_settings` table either.

## Why this blocks reusing either field for JoFotara

ISTD requires the number submitted with each invoice to be sequential and
gapless per taxpayer. Retail's `sale_number` satisfies that internally but
has a live cross-company collision bug; Clinic's `invoice_number` doesn't
satisfy it at all.

Two options were considered:

1. **Fix both products' existing numbering first**, then submit the fixed
   field to ISTD. Rejected: this is a visible behavior change to
   Wave1C-cleared, already-piloted installs (Clinic invoice number *format*
   would change; Retail's fix changes the on-record number for company_id !=
   1 installs). It fails the standing constraint that this feature must be
   invisible to any install that doesn't opt in.
2. **Give the e-invoicing module its own sequence**, independent of both
   products' local document numbers, used only for what gets sent to ISTD.
   The local `sale_number` / `invoice_number` is carried on the submission as
   a cross-reference field, unchanged, so a business can still reconcile "my
   receipt says SALE-000042" against "the government confirmed
   RETAIL-2026-000042" — but the local number itself never has to be
   correct-by-construction for tax purposes.

**Decision: option 2.** `einvoice_sequence` (see
`jofotara-integration-architecture.md`) is a new, per-company, per-invoice-family
table, gapless by the same "increment inside the same transaction that either
commits or rolls back" pattern already proven correct in `_next_ref()`. It is
touched only when the feature is enabled for that company, so an install that
never opts in never allocates a single row.

## Follow-ups — both since fixed, in a separate, later pass

Neither follow-up blocked JoFotara Phase 1 — the dedicated `einvoice_sequence`
is correct and compliant on its own regardless of whether these two
pre-existing bugs were ever fixed. They were addressed afterward, as their
own reviewed changes:

- **Retail:** `sales.sale_number` cross-company collision — fixed the same
  way `returns.return_number` already was (company fragment appended, e.g.
  `SALE-000042-<cid8>`). One-line change in `create_sale()`; verified against
  the full Retail suite (14 files, 0 failed) including a direct grep across
  backend, frontend, and this feature's own adapter for any format
  assumption (`.find()`-by-value comparisons only — no regex, no
  fixed-length parsing — so the format change was safe everywhere it's
  read).
- **Clinic:** `clinic_invoices.invoice_number` — replaced the
  timestamp+random scheme with a real sequential, gapless, per-company
  counter (`clinic_doc_sequences`, mirroring Retail's `doc_sequences`
  exactly, including the same company-fragment collision fix applied from
  day one rather than shipping the same bug twice). Added via the same
  idempotent lazy-create pattern `_ensure_credit_schema()` already
  established for `doc_sequences` — not a versioned schema.py migration.
  Verified against the full Clinic suite (13 files, 0 failed).

Both changes are visible format changes to already-issued-looking invoice
numbers going forward (not retroactive — existing rows are untouched); no
code path anywhere in either product parses or regex-matches the old
format, confirmed before either change shipped.
