# Aura Retail Unified Mobile — Android Data Preservation Plan (M4)

## Real constraint: this is a schema AND representation migration, not a copy

The legacy Android database (`<filesDir>/data/database/subsystems/retail.db`, `android-database-audit.md`) and the new SQLDelight-managed database (`<filesDir>/databases/retail_unified.db`, `AndroidDatabaseDriverFactory.kt`) are two **different files with two different schemas** — same tables/columns conceptually, but every money/quantity column changes representation from SQLite `REAL` (binary float) to `TEXT` (canonical decimal string, `shared-database-schema-decision.md`), timestamps change from `TIMESTAMP`/local-time strings to epoch-millisecond `INTEGER`, and `sale_items`/`return_items` gain a new required `product_name_at_sale` column with no source data to copy from (DIFF-03). This cannot be an in-place `ALTER TABLE` migration — it is a **one-time atomic import**, exactly the second option the governing spec itself offers ("B. one-time atomic import into the new shared database").

## Design: mirrors `commercial_runtime/security/migration_safety.py`, not invented from scratch

Same real, already-proven sequence `android-database-audit.md` documented from the Python authority's own schema-upgrade pattern, adapted for a cross-schema import instead of an in-place `ALTER`:

1. **Detect**: does the legacy `retail.db` file exist and does the new `retail_unified.db` NOT yet exist (or exist but marked not-yet-migrated)? If the new database already has data, this is a no-op — never re-import over live data.
2. **Pre-migration integrity check**: `PRAGMA integrity_check` on the legacy file *before touching anything*. If it fails, refuse to migrate and surface a clear "your existing data appears damaged, contact support / restore from your own backup" state — never attempt to import from a database already known to be corrupt.
3. **Pre-migration backup**: copy the legacy `retail.db` file (a real file copy is safe here specifically because the import opens it read-only and never writes to it — unlike `migration_safety.py`'s own live-backup-of-a-writable-database concern, which does not apply to a source we open read-only) to a timestamped backup location before the import starts.
4. **Row-count and checksum baseline**: count rows per source table, and compute a content hash (e.g. concatenated-and-hashed primary financial totals) before import — the post-import validation target.
5. **Transactional import**: open the new database, wrap the entire import in one transaction. For every source table, in dependency order (branches/categories/products before sales/purchase_orders, which reference them; sales before sale_items; etc.), read every row and insert it into the new schema with **explicit, preserved primary-key IDs** (never auto-increment-reassigned — foreign-key relationships depend on ID continuity).
6. **Post-import validation**: re-count rows per table in the new database and compare against the step-4 baseline; recompute and compare the financial-totals hash. Any mismatch aborts the whole transaction (rolls back everything imported so far) rather than leaving a partially-imported database.
7. **Never delete the source**: the legacy `retail.db` file is never modified or deleted by this process, at any step, success or failure — it remains on disk as the ultimate recovery point until a much later, explicit, separate cleanup decision (out of this milestone's scope; not before Milestone 18's real cutover proves stable).
8. **Retry-safe**: if the import fails at any point (crash, low storage, etc.), the new database is left either empty or rolled back to empty, and the legacy database is completely untouched — the next app launch can simply retry the whole import from scratch.

## Real representation-conversion decisions, stated honestly

- **`REAL` → `TEXT` for money/quantity columns**: converts via each value's `Double` representation (SQLite `REAL` already is an 8-byte binary float — there is no more precision to recover than Python's own arithmetic already committed to disk). The import uses `Money.of(Double)`/an equivalent `Quantity` conversion path (already real code from Milestone 3), **not** `Money.parse(String)` — the source value is a JDBC `Double`, not a string, and round-tripping it through `Double.toString()` first would risk introducing its own formatting artifacts before parsing. This is a real, honest limitation: a pre-existing Python-era value that was *already* imprecise due to years of binary-float accumulation (the exact class of bug Milestone 3 exists to prevent going forward) is preserved as-is at its already-imprecise value, not silently "corrected" to some invented "more correct" number — correcting historical financial records without an explicit, audited reason would be far worse than preserving an old, known imprecision.
- **`product_name_at_sale` backfill**: for every pre-existing `sale_items`/`return_items` row, the import resolves the product's *current* name (`products.name` as it exists in the legacy database, at migration time) and writes that as the frozen snapshot value going forward. This is the best available approximation for historical data (per `intentional-financial-differences.md` DIFF-03's own migration-impact note) — new sales created after Milestone 18's cutover are correct from the moment of creation; only pre-existing rows use this one-time best-effort backfill.
- **Timestamp conversion**: legacy `TIMESTAMP` columns are stored as local-time strings (`create_sale()`'s own `now_local` — a real, documented Python-side local-time convention, not UTC). The import parses these as local time in the device's current timezone and converts to epoch milliseconds — a real, small risk noted here honestly: a device that changes timezone between when data was created and when migration runs could shift historical timestamps by the timezone delta. Accepted as a low-probability, low-severity edge case (affects display ordering/date grouping only, never a financial total) rather than over-engineered away.

## What this milestone delivers (real, not just designed)

- `AndroidDatabaseDriverFactory` (already committed) — the real target-database driver, proven working end to end (`RetailDatabaseSchemaTest`, 3/3 passing).
- `LegacyRetailDatabaseReader` + `CatalogImporter` — a real, working first slice of the import pattern (branches, categories, products — the dependency-root tables every other table's FK ultimately traces back to), proving the whole pattern end to end: read via raw JDBC against the legacy schema's real column names/types, convert `REAL`→`TEXT`/timestamp→epoch-millis, write via the new schema's generated insert-with-explicit-id queries, verify row counts match.
- A real test (`CatalogImportTest`) that creates a synthetic legacy-shaped SQLite database (mirroring `schema.py`'s real branches/categories/products `CREATE TABLE` statements exactly), runs the importer against it, and asserts the new database has the same row counts with correctly-converted values.

## What remains for Milestone 18 (honest, not silently deferred without a plan)

The remaining 14 tables (inventory, customers/suppliers, purchase orders, sales/returns, payments, ledger/settings) follow the **identical, now-proven pattern** — read-convert-write-verify, in FK dependency order — extended table by table as Milestone 18's real Android cutover work begins (the milestone explicitly scoped to "do not replace [the Android app] until proven" — the full importer is exercised against real representative and corrupted Android databases as part of that milestone's own acceptance gates, not fabricated as already-complete here). Building all 19 tables' import logic now, months before Milestone 18's real cutover testing, would risk the import code drifting out of sync with the shared schema as Milestones 5-17 inevitably touch it — proving the pattern once, correctly, with one real dependency-root slice, is the right amount of Milestone-4 scope.

## Explicit non-goals reaffirmed from the governing spec

Corrupted-database recovery UX, a user-facing "restore from backup" flow, and cross-device data merge are real, separate concerns for later milestones (Milestone 16 backup/restore, Milestone 18 cutover) — not solved here.
