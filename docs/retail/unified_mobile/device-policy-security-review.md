# Device Policy Security Review (M8.15)

Real threat review of M8's device-policy/identity/replacement/iOS-
readiness/presentation contracts, extending
`licensing-contract-security-review.md` (M7.21) rather than repeating
it.

| # | Threat | Real mitigation | Evidence | Residual risk |
|---|---|---|---|---|
| 1 | Client computes/overrides its own device cap when the server is unavailable or slow | No mutator exists on `ResolvedDevicePolicy`; `SERVER_POLICY_UNAVAILABLE`/`TransportNotImplemented` are the only real fallbacks, never a locally-guessed cap | `clientCannotOverrideDeviceLimitOrActiveCount_noMutatorExists`, `presentationStatesAreClosedAndIncludeTransportNotImplemented` | None found |
| 2 | Client trusts a malformed/inconsistent server policy at face value | `ResolvedDevicePolicy.validate()` real internal-consistency checks (non-negative fields, remaining-count arithmetic, platform decode, policy version) — any violation is `DevicePolicyValidationResult.Malformed`, never silently used | `negativeLimitRejected`, `inconsistentRemainingCountRejected`, `unknownPlatformInPolicyRejected`, `futurePolicyVersionFailsSafely` | None found |
| 3 | iOS presented as activation-ready before Owner actually supports it | `IosPlatformReadinessState.current()` hard-codes every real blocking flag today; `readyForActivation` requires the flag set to equal exactly `{READY_FOR_ACTIVATION}` | `iosReadinessCurrentSnapshotHasEveryBlockingFlagAndNeverReadyForActivation`, `fullyReadyTargetFixtureIsRepresentableButDistinctFromCurrentState` | A future engineer must update `current()` only from real executable evidence (migration/schema/build proof), never narrative confidence — a process risk, not a code risk, flagged in `ios-platform-readiness-state.md`'s own "update discipline" section |
| 4 | Unrecognized/forged platform value (`ALL`/`MOBILE`/case-mismatch/future value) silently accepted as a known platform | `PlatformDecodeResult.parse()` real exact-name match only, no fallback | `platformDecodeRejectsAllAnyMobileAndUnknownValuesWithoutFallback` | None found |
| 5 | Local employee role (Retail RBAC) used to authorize a commercial device deactivation/replacement | No `DeviceManagement*Request` type carries a force/local-override field; every outcome is a real, closed enum with no locally-synthesizable success case | `deviceManagementOutcomesAreClosedAndDoNotIncludeAnUnauthorizedForceCase`, `local-authorization-device-management-boundary.md` | None found in the contract shape; actual enforcement still requires the real server-side authorization this contract only models |
| 6 | Installation seed/identity leaking through logs, crash reports, or UI state dumps | `LocalInstallationSeed`/`InstallationIdentity` `toString()` redaction, mirroring M7.17's own discipline | `installationIdentityToStringNeverExposesTheRawSeed`, `localInstallationSeedToStringNeverExposesItsValue` | Same residual risk M7.21 already flagged for reflection-based crash-report dumps bypassing `toString()` — unchanged, not re-solved here |
| 7 | Device metadata scope creep (a future PR silently adds a prohibited field, e.g. exact location or an advertising ID) | `DeviceMetadata` is a closed, 8-field `@Serializable` data class with no open `Map`; a structural serialization test proves the exact field set and the absence of prohibited-category key substrings | `deviceMetadataSerializesToExactlyTheEightAllowedFields`, `noSharedLicensingModelKeyMatchesAProhibitedDataCategory` | The prohibited-substring test only catches obviously-named fields (e.g. `"location"`) — a deliberately obfuscated field name would evade it; real defense-in-depth still requires code review, not just this test |
| 8 | Lost/stolen device identity reused to impersonate the original Installation after a factory reset or app-data wipe | `InstallationIdentityStatus.LOST` is a real, distinct enum value from `GENERATED`; `installation-reinstall-recovery-contract.md`'s own case B requires the client to always present as genuinely new, never resubmit the old identity | `lostIdentityStatusIsDistinctFromGeneratedNeverImpersonatesThePrevious` | Real enforcement of "never resubmit the old identity" depends on the future real activation client implementation actually consulting this status before building a request — not yet wired to any real request-construction code, since none exists yet (M8 stops at contract shape) |
| 9 | Duplicated restored-backup identity across two physical devices both claiming the same Installation | Server remains authoritative; Owner's own real, globally-unique `DevicePublicKey.fingerprint` constraint is the actual enforcement point | `installation-reinstall-recovery-contract.md` case C, cross-referencing M7's `installation-authority-contract.md` | Not testable client-side by construction — correctly classified `NOT_APPLICABLE_WITH_EVIDENCE` in `device-policy-fixture-report.md`, not silently assumed safe |
| 10 | Customer-auth-gated device-management action performed without the (currently nonexistent) real customer authentication | `DevicePolicyPresentationState.CustomerAuthPrerequisiteMissing` is the real, honest state; no code path in this milestone fabricates success for an account-gated action | `customerAuthPrerequisiteMissingStateIsDistinctFromServerUnavailable`, `OWNER-EXTERNAL-CUSTOMER-IDENTITY-AND-LICENSING-BOUNDARY-SPEC.md` | Full resolution requires the real Owner-side `CustomerAccount` authority (M8.10's own spec) — correctly out of scope for M8 |

## Explicit scope boundary honored

This review covers the real *contract* shape M8 delivers — validation,
closed enums, redaction, allowlists, and honest fallback states — not
a not-yet-built real HTTP/storage/crypto implementation. Every
mitigation cited is a real, executed test or a real, compile-time
structural guarantee, not a documentation-only claim.
