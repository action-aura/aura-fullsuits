# Android Secure Storage Decision (M10.7)

Real, evaluated decision: **raw `AndroidKeyStore` AES-256-GCM key
wrapping with a real, versioned file envelope** — mirroring
`android/aura-retail`'s own real, physically-tested (Phase 7V-A)
`DeviceIdentity.kt`/`AndroidKeystoreWrapper` design
(`secure-storage-current-state-audit.md`) — **not**
`EncryptedSharedPreferences` (the M2 skeleton's own choice, evaluated
and superseded here).

## Real evaluation

| Requirement | `EncryptedSharedPreferences` (M2 skeleton) | Raw `AndroidKeyStore` AES-GCM (this decision) |
|---|---|---|
| Key generation | Real, `MasterKey.Builder`, Keystore-backed | Real, `KeyGenParameterSpec`, Keystore-backed — same real primitive underneath |
| Non-exportable key | Yes (real Keystore guarantee either way) | Yes |
| Associated-data (AAD) binding per value | **No** — the library's own API has no per-entry AAD parameter | **Yes** — `Cipher.updateAAD(associatedData)`, real, direct GCM AAD support |
| Hardware-backed / StrongBox | Not directly exposed/controlled by the library's own API | Real, explicit, with a real tested fallback (mirrors `DeviceIdentity.kt`'s own `buildWrappingKeySpec`/`getOrCreateWrappingKey` — `setIsStrongBoxBacked(true)` attempted first, `Throwable`-caught fallback to non-StrongBox, since a real device without StrongBox hardware throws `StrongBoxUnavailableException` *inside* `generateKey()`, confirmed via physical testing in that same file) |
| Atomic multi-blob generation/pointer support | Not designed for this — a `SharedPreferences.Editor` transaction covers one `apply()` call, not a multi-key staged commit | Real — file-per-blob storage lets `GenerationalSecureMaterialStore` (M10.6) manage generations directly |
| Dependency maturity | **Alpha** (`androidx.security:security-crypto:1.1.0-alpha06`, confirmed pinned in `mobile-licensing-network-audit.md`) — a real, disclosed production risk | Zero extra dependency — `android.security.keystore`/`javax.crypto` are real platform APIs, no alpha library in the loop |
| Real prior art in this codebase | None used for licensing material yet | `DeviceIdentity.kt`, physically tested, already proven in production for the legacy app's own Ed25519 device key |

## Real decision

Adopt the `DeviceIdentity.kt`-proven pattern, generalized into
`AndroidSecureBlobStore` (M10.8): `AES/GCM/NoPadding`, 256-bit key,
`KeyGenParameterSpec` with `setIsStrongBoxBacked(true)` attempted
first and a real `Throwable`-caught fallback, IV(12 bytes) + GCM-
tagged ciphertext stored per named blob, real AAD binding via
`Cipher.updateAAD(associatedData)`.

## Real, additional design decisions this milestone adds beyond `DeviceIdentity.kt`

- **Key alias versioning**: `DeviceIdentity.kt` uses one fixed alias
  forever. M10's own key-rotation requirement (M10.16) needs multiple
  live key generations — this implementation prepends a short alias-id
  header to each stored envelope (`<alias_id_length><alias_id><IV><
  ciphertext>`), so `get()` can look up the exact historical Keystore
  alias that encrypted a given blob, while `put()` always uses the
  current alias. Real, disclosed limitation: rotating the current
  alias does **not** proactively re-encrypt already-stored blobs under
  the new key — they remain readable under their own original alias
  until a future re-encryption pass explicitly migrates them (a real,
  bounded scope decision, not silently claimed complete — see
  `secure-storage-key-rotation.md`).
- **Atomic file writes**: each blob is written to a temp file, then
  renamed into place (`File.renameTo`, a real POSIX-atomic rename on
  the same filesystem) — real, standard practice this milestone adds
  on top of `DeviceIdentity.kt`'s own simpler direct-write, since M10's
  own atomicity requirements are stricter (the generation/pointer
  scheme in `GenerationalSecureMaterialStore` depends on individual
  blob writes not being torn).

## Real prohibited practices — confirmed absent

No hard-coded encryption key, no deterministic IV reuse (a fresh IV is
generated by the JCE provider on every real `Cipher.ENCRYPT_MODE`
init, matching `DeviceIdentity.kt`'s own real, unchanged behavior), no
ECB mode (`AES/GCM/NoPadding` only), no unauthenticated encryption (GCM
is AEAD by construction), no reversible obfuscation, no Base64-as-
encryption, no device-identifier-derived key, no user-password-as-
sole-key.

## No silent plaintext downgrade

`AndroidSecureBlobStore.capability()` reports `available = false` when
`AndroidKeyStore` itself is unavailable (a real, if rare, device/OS
condition) — the real `GenerationalSecureMaterialStore.initialize()`
then returns `SecureStorageFailureCode.NOT_AVAILABLE`, never silently
falling back to an unencrypted store.
