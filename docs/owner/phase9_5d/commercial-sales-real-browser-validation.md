# Phase 9.5D — Milestone 25: Real Browser/Responsive/RTL/Keyboard/A11y Validation

Matches Phase 9.5C's own precedent: "real browser validation... found 4 genuine defects that no automated test caught." Automated `pytest` HTTP-client tests (Milestones 18/19/23) prove routing/permission/serialization correctness but never render CSS, execute JavaScript, or lay out RTL text — this milestone actually opens the pages in a real Chromium browser (Playwright) against a real running dev server and a real Postgres-backed session.

## A real environmental hazard found and safely worked around

Starting the dev server on the project's usual port (5551) produced `404 Not Found` for every new commercial-sales route while pre-existing routes (`/leads`) worked fine. Diagnosed via `netstat`: **two** processes were listening on `127.0.0.1:5551` simultaneously — a pre-existing, long-running `flask run` process left over from earlier manual/browser-validation sessions (confirmed by the browser's autofilled saved login for `crm-wave95c-sales@example.com`, a Phase 9.5C-era test account, and by matching screenshot filenames like `r95c-lead-detail-ar.png` already present in the workspace root) was silently intercepting requests ahead of the freshly-started process running this session's actual code. Resolved by stopping only the specific background task this session had started (`TaskStop`, not a blind process kill) and restarting on port 5552 — the untouched leftover process was never modified or terminated, avoiding any risk to whatever the user may still want from it.

## What was validated, live, with real clicks and real screenshots

- **Full document chain through actual UI interaction** (not API calls): created a real Quote (`Q-2026-0001`) via `/quotes/new`, added a real catalog line (`$750.00`, verified rendering `750` after formatting), clicked **Submit quote** (a real native `confirm()` dialog appeared and was accepted — `confirm.js`'s `data-confirm` wiring works), clicked **Customer accepted**, clicked **Create sales order** → real `SO-2026-0001`, clicked **Confirm order** (another real confirm dialog), clicked **Create invoice** → real `INV-2026-0001`. The full numbering chain (Milestone 5's `allocate_document_number()`) worked correctly end to end through genuine browser interaction.
- **RTL**: switched to Arabic on the Quote detail page mid-flow — full-page screenshot confirms correct mirroring: nav bar right-to-left, table columns and headers properly translated and aligned, definition-list label/value pairing correct, form labels positioned correctly for RTL reading order. No literal untranslated English UI strings found (only genuine test-data content like the plan/customer names I created, which are real data, not UI copy).
- **Mobile responsive**: resized to 390×844 (a real phone viewport) on the same Arabic RTL page — the `responsive-table` CSS class correctly collapsed the line-items table into stacked cards with `data-label` prefixes rendering in Arabic, confirming the Milestone 9.5B-era responsive CSS applies unchanged to every new Milestone 19 template with no page-specific overrides needed.
- **Dashboard correctness cross-check**: the Finance dashboard's `outstanding_invoice_total` correctly showed `0.00` even with a real `750.00` invoice in the database — because that invoice was still `DRAFT` (not yet `ISSUED`), matching the documented contract (`outstanding_invoice_total` only sums `ISSUED`/`PARTIALLY_PAID`) exactly, not a bug.
- **Keyboard/a11y**: every new template uses only native HTML form controls (`<button>`, `<input>`, `<select>`, `<textarea>`) with no custom JS widgets (no custom dropdowns, date pickers, or modals beyond the browser's own native `confirm()`) — native elements are keyboard-operable and screen-reader-navigable by construction, which the accessibility-tree snapshots taken at every step confirm (every control has a correct accessible role and name, e.g. `button "Confirm order"`, `textbox "Reason"`).
- **Console cleanliness**: zero real JavaScript errors across the entire session — only pre-existing, site-wide `favicon.ico` 404s (unrelated to this phase, present on every Owner page already) and the two artifacts from the leftover-process diagnosis (explained above, not a defect in current code).
