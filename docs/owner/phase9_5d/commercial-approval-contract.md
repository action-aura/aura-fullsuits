# Phase 9.5D — Milestone 6: Commercial Approval Contract

`app/commercial_sales/approvals.py`, on the `CommercialApproval` model (migration `b7e4a2c91f30`) — a separate, per-document approval record, matching the existing `RenewalRequest`/`PendingActivation`/`PilotRecord` convention, deliberately not folded into `Quote.status` (Milestone 1's audit).

## Functions

- `compute_line_commercial_fingerprint(*, plan_id, addon_id, quantity, unit_price, overridden_unit_price, discount_amount, currency) -> str` — deterministic SHA-256 content fingerprint of the exact commercial values an approval decision is about. Every Decimal is quantized to the column's own 2-decimal-place precision before hashing (see "second real bug" below).
- `create_approval_request(*, target_type, target_id, target_version_at_request, commercial_fingerprint, reason_code, requested_values, original_values, requested_by_staff_user_id) -> CommercialApproval` — `PENDING`. `target_version_at_request` is retained for audit/debugging value only — it is no longer the staleness authority.
- `decide_approval(approval, *, approved, decision_reason, decided_by_staff_user_id) -> CommercialApproval` — `PENDING`→`APPROVED`/`REJECTED`. Enforces, in this order: self-approval block (Non-Negotiable Principle 12 — checked in the service layer regardless of permission grant, since "UI hiding is not authorization"), valid transition, reason-required-on-reject, staleness. **No `current_target_version` parameter** — the function looks up the target's *current* persisted state itself (via `target_type`/`target_id`) and recomputes the fingerprint, rather than trusting a caller-supplied value that could be stale or simply wrong by mistake. A target that no longer exists (a deleted line) is treated as `APPROVAL_STALE`, never as "nothing to check."
- `cancel_approval_request(approval, ...)` — `PENDING`→`CANCELLED` (e.g. the requester edits the line to remove the exception before anyone decides).
- `unresolved_approvals_for_targets(target_type, target_ids) -> list[CommercialApproval]` — returns every `PENDING`/`REJECTED` approval for the given targets; `APPROVED`/`CANCELLED`/`EXPIRED` are excluded (resolved, not blocking). Used by the Quote acceptance gate.

## Why a content fingerprint instead of a version counter (verification pass before closing this milestone)

`QuoteLine.version` alone is only a valid staleness signal if *every* approval-relevant mutation reliably bumps it — true only by the accident that no line-edit function exists yet in this codebase, not because the mechanism is actually robust. A content fingerprint is strictly stronger: it's computed directly from the material values themselves (product/plan, quantity, list price, proposed/override price, discount, currency) and is structurally incapable of missing a real change, regardless of which future code path makes it (an `update_quote_line()` added later needs no corresponding "remember to bump the staleness counter" discipline — any write to a fingerprinted field is automatically caught). It is equally incapable of false-positiving on anything *not* in the payload — viewing, audit writes, sibling-line changes, unrelated Quote-level status transitions (submit, etc.) can never appear in the hash.

Proven in both directions by `TestApprovalValidityBoundToCommercialSubstance`:
- **Material changes invalidate**: direct mutation of `quantity`, `overridden_unit_price`, `discount_amount`, and `plan_id` (the line now referring to an entirely different product) each independently trigger `APPROVAL_STALE`. A deleted line also triggers `APPROVAL_STALE`, not a silent pass.
- **Unrelated actions do not invalidate**: adding an unrelated sibling line to the same Quote, submitting the Quote (a `Quote.status`/`.version` transition), and writing unrelated audit-log entries referencing the same line all leave the approval fully decidable.

## Second real bug found and fixed while building the fingerprint

SQLAlchemy expires ORM instances by default after `commit()` — the next attribute read re-fetches from the database and re-coerces the value through its actual column type. `Decimal("0")` and `Decimal("0.00")` are numerically equal but `str()` differently ("0" vs "0.00"), so a fingerprint computed from a caller-supplied Decimal of unknown precision (pre-commit) would never match one recomputed from the post-commit, always-2-decimal-place database value — even with zero material change. This surfaced as *every* test failing with `APPROVAL_STALE`, including ones with no mutation at all. Fixed by quantizing every Decimal to the column's own precision (`ROUND_HALF_UP`, 2 places — the same codebase-wide convention `app/commercial_sales/calculator.py` already uses) before it enters the hash payload, on both the request-time and decision-time computation paths.

## Integration with the Quote domain

`quotes.py::add_quote_line()` calls `catalog_for_sales.requires_line_approval()` after computing the line; if true, auto-creates a `PENDING` `CommercialApproval(target_type="QUOTE_LINE", target_id=line.id, ...)` with `reason_code` derived from which condition triggered (`PRICE_OVERRIDE`, `ZERO_PRICE_LINE`, `DISCOUNT_ABOVE_LIMIT`). `quotes.py::record_customer_decision(accepted=True)` calls `unresolved_approvals_for_targets("QUOTE_LINE", <this quote's line ids>)` and raises `APPROVAL_REQUIRED` if anything is still `PENDING`/`REJECTED` — an accepted Quote can never have an unresolved exception underneath it.

## Real bug found and fixed: version pinned to the wrong row

The first implementation pinned `target_version_at_request` to the **Quote's** `version`. Since `Quote.version` increments on every mutation — including `submit_quote()` and adding an unrelated sibling line — every pending approval was immediately, incorrectly marked stale before a decider could ever act on it (caught by `test_accept_succeeds_after_approval_granted`, which failed with `APPROVAL_STALE` on the very first correct-usage attempt). Fixed by giving `QuoteLine` its own `version` column (migration `c92d5f18a4e6`, additive — matching the existing per-child-row optimistic-lock pattern already used by `LeadContact.version`/`CustomerContact.version`/`CustomerLocation.version`) and pinning the approval to the **line's** version instead. Since this milestone has no `update_quote_line()` (line editing is out of scope — reserved for Milestone 18/19's `PATCH /quote-lines/{id}`), `QuoteLine.version` never actually changes after creation in the current codebase, so staleness never fires today — correct, since nothing has actually changed. The mechanism itself is proven correct by `test_stale_approval_rejected_after_quote_changed`, which manually bumps `line.version` to simulate a future edit and confirms `decide_approval()` still rejects it as stale.
