## Fixes made during this phase's own commit-by-commit security review
An automated per-commit review flagged several real issues while this phase's commits were being made; all were investigated and fixed in the same phase (not deferred):
- **Open redirect** (`auth/routes.py`): the `next` query/form parameter was redirected to unvalidated after login and reauth. Fixed with `_safe_next()`, which only accepts a same-site relative path (rejects absolute URLs and `//host` protocol-relative values). Test: `test_security.py::test_login_open_redirect_rejected`.
- **MFA brute-force** (`auth/routes.py::mfa_verify_submit`): TOTP code guesses had no rate limit, unlike password login. Fixed by reusing the same persistent throttle (`is_locked_out`/`record_attempt`) keyed on the pending account's email. Test: `test_mfa_verify_brute_force_locked_out`.
- **MFA re-enrollment authorization gap** (`auth/routes.py`): an already-logged-in session with no fresh MFA confirmation could silently swap in a brand-new MFA device (`/auth/mfa-enroll`) on an account that already had one -- a hijacked session could lock out the legitimate owner. Fixed: re-enrollment of an *existing* credential now requires `has_recent_auth()`; first-time voluntary enrollment (no existing credential) is unaffected, since there is nothing to prove recent possession of yet. Test: `test_reenrolling_mfa_while_logged_in_requires_recent_auth`.
- **Privilege escalation via role assignment or invitation** (`staff/services.py`): granting `SUPER_ADMIN` relied solely on whoever held `staff.assign_roles`/`staff.create` -- correct today (only Super Admin holds those), but not structurally guaranteed against a future role reassignment. Fixed with an explicit `SelfEscalationError` guard in both `assign_roles()` and `create_invitation()`: granting `SUPER_ADMIN` is refused unless the actor is already a Super Admin, independent of what the permission table says. `staff.invite` also gained `@require_recent_auth`. Tests: `test_non_super_admin_cannot_grant_super_admin_role_via_service`, `test_super_admin_can_grant_super_admin_role`.
- **Authorization-bypass via the generic customer-update route** (`customers/routes.py`): `POST /customers/<id>` accepted `lifecycle_status` in its field whitelist, letting anyone with only `customers.update` reach the same effect as the more specific `customers.archive` permission. Fixed by removing `lifecycle_status` from that whitelist -- status changes now only happen through the dedicated `archive()` route.
- **Audit-trail cascade-delete risk** (`models/subscriptions.py`, `models/licensing.py`, `models/installations.py`): `status_history`/`issuance_events`/`activation_events` relationships were declared with `cascade="all, delete-orphan"`, meaning a future parent-row delete (no route does this today, but nothing prevented adding one) would silently destroy the audit trail alongside it -- directly contradicting Part D's "do not hard-delete... audit history by default." Fixed by removing delete-orphan from the history/event relationships specifically (normal child-detail relationships like `entitlements`/`devices` keep it, since those aren't audit trails).

## Not addressed this phase (disclosed)
Distributed/multi-process rate limiting (single-process DB-backed limiter only, acceptable at internal-staff scale); automated dependency vulnerability scanning (no CI pipeline exists yet for this app); network-level protections (this app is not deployed to a reachable network in Phase 5). See `owner-residual-risk-register.md`.
