# Owner App — Screen & Route Inventory (Stage A Audit)

Read-only audit of every screen/route in the Aura Owner Flask+Jinja2 app
(`owner/app/`), produced ahead of the UI/UX modernization phase on branch
`feat/owner-ui-ux-modernization`. Every claim below is cited to a real
`path:line` in this repository — nothing here is inferred from route names
alone; every listed template was read in full.

## Method

- Enumerated every Flask blueprint under `owner/app/` via
  `grep -rn "@bp.route\|add_url_rule" owner/app --include=*.py` (389 route
  registrations across 25 files) and cross-checked against
  `grep -rl "render_template(" owner/app --include=*.py`, which narrowed
  the HTML-screen-producing blueprints to 18 files: `auth`, `dashboard`,
  `employees/self_routes` (blueprint name `profile`), `leads`, `customers`,
  `commercial_sales`, `catalog`, `releases`, `operations_ui`,
  `subscriptions`, `licensing`, `licensing_admin`, `installations`,
  `commercial_ops/ui_routes`, `staff`, `employees`, `audit`, `system`.
  Blueprints in `api/`, `api_external/`, `api_operations/`, and
  `locale_routes.py` are JSON/API or redirect-only and are excluded from
  this screen inventory (noted explicitly where relevant below).
- Every route in scope was read directly (route handler + the template(s)
  it renders) to determine role/permission access, ownership scoping,
  and real usability/accessibility/responsive/performance issues — not
  inferred from naming conventions.
- **RBAC model** (`owner/app/security/rbac.py`): `require_login` (any
  authenticated staff), `require_permission(code)` (must hold one specific
  permission code), `require_any_permission(*codes)` (holds any of the
  listed codes — the `_own`/`_all` permission-pair pattern, e.g.
  `leads.view_own` vs `leads.view_all`), `require_recent_auth` (fresh
  MFA/reauth within a recent window, layered on top of `require_login`,
  used for highly sensitive actions: role changes, disabling staff,
  license issuance/reveal, entitlement changes, audit export, database
  restore — per the module's own docstring at rbac.py:88-91).
- **Role → permission catalog**: `owner/app/staff/seed_data.py` defines
  five seeded roles — `SUPER_ADMIN` (wildcard, every permission via
  `StaffUser.is_super_admin`), `SALES`, `SUPPORT`, `FINANCE`, `VIEWER` —
  and ~100 fine-grained permission codes. "Role access" columns below are
  derived by cross-referencing the permission code(s) a route checks
  against this seed file, not guessed.
- **Global navigation**: `owner/app/templates/layout/base.html:92-134` is
  a single flat `nav.tabs` block that lists **every** screen link to
  **every** logged-in staff member regardless of role or permission —
  there is no `{% if %}` filtering by permission in the nav itself (only
  the `{% if staff %}` gate for "logged in at all", base.html:91). Access
  control is enforced entirely server-side per route; a user without the
  needed permission who clicks a visible nav link (or an in-page action
  button — see the many "permission-blind form rendering" findings below)
  gets a 403. This single fact explains a large share of the "usability
  issues" cited throughout: buttons and nav links are visible to roles
  that cannot use them.
- No Jinja macros or `{% include %}`/`{% import %}` exist anywhere in
  `owner/app/templates` (`grep -rn "{% import\|{% include\|{% macro"
  owner/app/templates` → 0 matches) — every template is a standalone
  `{% extends "layout/base.html" %}` file. See
  `docs/owner/ui-modernization/current-ui-audit.md` for the full frontend
  architecture audit.

## Auth / Security

**Notes before the table:**
- `owner/app/locale_routes.py` `GET /locale/<code>` is a pure redirect-setting-a-cookie action (locale_routes.py:31-54) — no template rendered, confirmed skipped from this table per the task's instructions.
- `POST /auth/logout` (auth/routes.py:310-327) is redirect-only (no template ever rendered on any path) — skipped from the table body per the "skip redirect-only routes" rule, noted here only: it revokes the session, records an audit event, and redirects to `auth.login_form`.
- No dedicated "lockout", "session-expired", or "access-denied" templates exist anywhere in `owner/app/templates`. Lockout reuses `auth/login.html`/`auth/mfa_verify.html`'s inline `{% if error %}` block with the string "Too many attempts -- try again later." (auth/routes.py:72, 129). A session that has expired/been revoked simply causes `load_current_staff()` to return `None` (auth/session.py:102-115), so the user is bounced to the ordinary login form via `require_login`'s redirect (rbac.py:34-44) with no "your session expired" messaging at all. `abort(403)` (rbac.py:56, 80) falls through to Flask's built-in default error page, not an app template. This is itself a real UX gap, flagged for the redesign rather than fabricated as if a template existed.
- `/auth/mfa-recovery-codes` and `/auth/reauth` are rarely-hit, high-sensitivity screens (recovery codes viewable exactly once post-enrollment; reauth only appears when a `require_recent_auth`-gated action needs a fresh MFA challenge). `/auth/accept-invitation/<token>` is admin-invitation-only, very low traffic.

**Cross-cutting findings worth calling out explicitly:**
- **Admin-only, UI-unreachable routes**: `leads.assign` (POST /leads/<id>/assign) and `leads.archive` (POST /leads/<id>/archive) have zero corresponding forms in any template — only exercisable by direct POST/API today. `crm_shared.cancel_followup` also has no confirmed UI trigger in either detail template.
- **Permission-blind form rendering**: nearly every write form in `leads/detail.html` and `customers/detail.html` is rendered unconditionally regardless of the viewer's actual permission (status change, convert, reassign, archive, verify-location, and all child-record add forms) — read-only roles (VIEWER, FINANCE, and SUPPORT on customer contacts) see fully live controls that 403 on submit, mirroring the same "visible-then-403" pattern already known from the global nav.
- **Inconsistent error UX between the two blueprints**: Lead child-record actions (contacts/interactions/followups/notes/location) silently swallow `LeadError`/`LocationValidationError` with no feedback at all (`except LeadError: pass`), while the equivalent Customer actions redirect with `?error=exc.code`, which the leads.detail route rebuilds into a localized banner — so failures on the Leads side are invisible to the user, on the Customers side they're at least shown.
- **List pagination inconsistency**: Leads list is paginated but the status filter is applied after pagination (in-memory on the current page only); Customers list has no pagination whatsoever (unbounded query every request).

**Notable cross-cutting findings for the redesign brief:**
1. **Broken redirect for SALES on payment creation** — `submit_payment_route` (routes.py:513) redirects to `payment_detail`, which requires `payments.view` (routes.py:517), a permission SALES never holds (seed_data.py:169-213). This is a functional bug, not just a UX gap.
2. **Missing SoD/second-approver controls on Refunds and Commission Payout Batches** — both are gated by a single permission (`refunds.approve`/`commissions.pay`) that covers both the creating and approving actions, unlike Quotes/Orders/Invoices/Payments which cleanly separate `*.create` (SALES) from `*.approve`/`*.issue`/`*.confirm` (FINANCE).
3. **Inconsistent status-badge coloring** — list screens color-code `.badge` by status; the corresponding detail screens for Quote/Order/Invoice/Plan render a bare, uncolored `.badge` for the identical status value (quote_detail.html:6, order_detail.html:6, invoice_detail.html:6, plan_detail.html:8), while Refund's detail screen does color it (refund_detail.html:6) — no consistent rule today.
4. **Action buttons rendered without a permission check in the template** — `payment_detail.html` (confirm/reject) and `plan_detail.html` (add price) show mutating-action forms to any viewer who can reach the page, unlike quote/order/invoice/refund detail templates which correctly gate on a `can_approve`/`can_issue` flag passed from the route.
5. **VIEWER and SUPPORT roles have zero permissions anywhere in the commercial_sales blueprint** (confirmed against seed_data.py:215-234 and :296-319) — every route in the Sales table above is unreachable for those two roles, yet the global `nav.tabs` in `layout/base.html:97-105` still lists all 9 commercial-sales nav links to them regardless, producing a guaranteed 403 on click for two of the five seeded roles.

**Cross-cutting findings worth carrying into the redesign brief:**
1. **`.responsive-table` is used everywhere in this domain group (every single list/detail table, ~25+ instances) but `data-label` is never set anywhere** (`0` matches across `templates/licensing/`, `templates/licensing_admin/`, `templates/installations/`, `templates/commercial_ops/`) — the CSS rule at `layout/base.html:57` (`td[data-label]::before`) is dead code for this entire domain; on mobile every table collapses to unlabeled stacked values.
2. **Unbound `<label>`s** are systemic in the "new"/create forms introduced by `commercial_ops_ui` (renewals_new.html, pilots_new.html, pilot_convert.html) but correctly bound in the older `licensing`/`installations` forms (new.html files) — suggests a regression/inconsistency introduced in a later phase, not a one-off.
3. **Confirmation dialogs are 100% `window.confirm()` via `data-confirm`** (`static/js/confirm.js:15-16`) — if JS fails to load, every destructive action (revoke, suspend, replace, rotate, cancel) submits immediately with zero confirmation. This is a single-point-of-failure across the whole domain group, not a per-screen issue.
4. **Three routes are completely unreachable from any UI navigation or link**: `licensing_admin.entitlement_preview`, `licensing_admin.assign_offline_policy` (no UI entry point at all for offline-policy assignment), and `commercial_ops_ui.activation_policy_list`/`activation_policy_create` (SUPER_ADMIN's most consequential security-posture screen has no nav link anywhere).
5. **No dedicated permission exists for Notifications or My Queue** — both are gated on the generic `subscriptions.view`, which VIEWER holds, letting a nominally read-only role assign/acknowledge/resolve notifications.
6. **License lifecycle actions (issue/suspend/revoke/replace/reactivate) are entirely SUPER_ADMIN-only** in the current seed data — SUPPORT (the documented "day-to-day licensing operations role") can only view/register/update installations, not touch license state at all beyond `licenses.view`. This is a materially different picture than the background brief implied ("SALES ... no suspend/revoke" suggested SUPPORT might have them) and should be confirmed with the product owner before redesigning the License workflows around a broader operator base.
Two systemic findings worth calling out before the table: (1) every route across all four blueprints resolves to **SUPER_ADMIN only** — none of `staff.*`, `employees.view_all/create/update/suspend/terminate`, `security_sessions.revoke`, `audit.view/export`, or `system.view/backup/restore` appear in the SALES/SUPPORT/FINANCE/VIEWER permission lists in `owner/app/staff/seed_data.py:169-320` (SALES only gets `employees.view_own`, `employees.view_presence` at seed_data.py:188); (2) `employees.assign_role` (seed_data.py:93) and `employees.manage_commission_plan` (seed_data.py:94) are dead permissions as far as this blueprint goes — `owner/app/employees/routes.py` never checks either; the "Roles and permissions" form in `employees/detail.html:35` actually posts to `staff.update_roles` (gated by `staff.assign_roles`), and commission plan is settable only once at creation (`employees/routes.py:102`), with `employees.assign_role` only enforced in the separate JSON API at `owner/app/api_operations/routes.py:331`.

## App-wide cross-cutting findings (synthesized across all domain groups)

These patterns recur across three or more domain groups above and should
be treated as systemic redesign inputs, not per-screen defects:

1. **Nav/buttons are permission-blind; the server is the only real
   gate.** `layout/base.html:92-134`'s global nav shows every screen to
   every logged-in staff member, and the same pattern repeats inside
   individual pages: write-action forms/buttons on Leads, Customers,
   Quotes/Orders/Invoices/Payments, License, Installation, Pilot, Plan,
   and Cash-Closing detail screens are rendered unconditionally in markup
   even when the viewer's actual permission set can't satisfy the
   corresponding POST route, producing a "visible control, 403 on click"
   experience for VIEWER/SUPPORT/FINANCE/SALES depending on screen. A
   redesign should conditionally render (or clearly disable-with-reason)
   actions based on the permission set already computed server-side and
   passed to the template — several screens (Quote/Order/Invoice/Refund
   detail) already do this correctly via a `can_approve`/`can_issue` flag
   and should be the reference pattern, not the exception.
2. **`.responsive-table` without `data-label` is dead code across large
   swaths of the app.** The Licensing domain group (Licenses,
   Installations, Activation Service, Renewals, Pilots, Emergency
   Extensions, Pending Activations, My Queue, Reconciliation — ~25+
   tables) opts every table into `.responsive-table` but never sets
   `data-label` on any `<td>`, so the CSS rule at `base.html:57`
   (`td[data-label]::before { content: attr(data-label) }`) has nothing
   to render on narrow viewports — tables collapse to blank, unlabeled
   stacked values on mobile. Finance/CRM screens generally do set
   `data-label` correctly. Subscriptions' list/detail tables declare
   `.responsive-table` but also omit `data-label` — a regression relative
   to the pattern's own origin (documented in `base.html:47-51` as
   "Phase 9.5B ... reused by the new employee screens").
3. **Unbound `<label>`s are the majority pattern, not the exception.**
   Across almost every domain, form labels are visually adjacent to their
   inputs but not linked via `for`/`id` (confirmed missing in Leads,
   Customers, Sales, Expenses, Cash Closing, Management Notes, Renewals,
   Pilots, Emergency Extensions creation forms). A small number of forms
   get it right (`customers/new.html`, `catalog/plan_new.html`,
   `subscriptions/new.html`, most of the older `licensing`/`installations`
   forms) — these should be the template for a shared form-field pattern
   in `form-validation-system`, not a one-off.
4. **All destructive-action confirmation is `window.confirm()` via
   `data-confirm`, with no server/UI fallback.** `static/js/confirm.js`
   is the sole confirmation mechanism app-wide; if JS fails to load (CSP
   allows only `script-src 'self'`, so this is a real single point of
   failure, not hypothetical), every revoke/suspend/void/terminate/
   restore/reject action submits immediately with zero confirmation.
   Confirmation coverage is also inconsistent even where JS does load:
   several genuinely destructive actions have no `data-confirm` at all
   (Staff "Reset MFA", Employee "Revoke all sessions"/per-session revoke,
   Pilot "Approve"/"Activate"/"Extend", slot-exception "Revoke").
5. **Maker-checker (segregation of duties) is real but incomplete.**
   Quotes/Orders/Invoices/Payments correctly separate SALES (`*.create`)
   from FINANCE (`*.approve`/`*.issue`/`*.confirm`), and Cash Closing
   blocks self-approval at both the service layer and the template.
   Refunds and Commission Payout Batches, however, gate both the
   "create/request" and "approve/pay" actions behind the same single
   FINANCE permission (`refunds.approve`, `commissions.pay`) with no
   second-approver requirement — a real architectural gap worth deciding
   on explicitly before the `commercial-flow-ui`/`finance-ui` redesign
   locks in a workflow shape.
6. **A meaningful number of routes have zero UI entry point.**
   `leads.assign`, `leads.archive`, `crm_shared.cancel_followup`,
   `licensing_admin.replace_device`, `licensing_admin.assign_offline_policy`,
   `licensing_admin.entitlement_preview`,
   `commercial_ops_ui.activation_policy_list`/`_create`,
   `operations_ui.regenerate_snapshot_route`, and
   `subscriptions.correct_payment_route` are all real, fully-implemented
   routes with no form, link, or button anywhere in the rendered
   templates that reaches them — several are SUPER_ADMIN's most
   consequential actions (activation policy defines the security posture
   for all future activations of a product) yet are only reachable by a
   hand-typed URL today. These need an explicit product decision
   (build the missing entry point, or confirm intentionally
   admin-only/deprecate) before the redesign scope is finalized.
7. **Error handling is inconsistent between raw JSON and rendered
   HTML on the same class of failure.** Several POST routes (Staff
   invite/role-change/disable, Employee edit/activate/suspend/terminate,
   Subscription create/transition, License/Installation creation on
   invalid FK) return a bare `jsonify({...}), 4xx` to what is otherwise
   an ordinary HTML form submission, so the browser renders raw JSON
   instead of the form redisplayed with an inline error — a real,
   user-visible defect distinct from the (also real) lack of field-level
   validation messaging almost everywhere else.
8. **Status badges are color-only in some places, color+text in most,
   and inconsistently applied even for the identical status value on
   sibling screens** (e.g. Quote/Order/Invoice/Plan detail headers render
   a bare uncolored `.badge` for a status that IS colored on the
   corresponding list screen; Subscriptions' badge logic only
   distinguishes `ACTIVE` vs. a generic "draft" bucket, losing
   SUSPENDED/EXPIRED/CANCELLED as visually distinct states).
9. **Two structurally different access profiles are visually grouped
   as peers today.** Notifications and My Queue are reachable by
   SALES/SUPPORT/FINANCE/VIEWER/SUPER_ADMIN (gated only on the broad
   `subscriptions.view`, with no dedicated `notifications.*` permission —
   itself worth flagging since it lets a nominally read-only VIEWER
   assign/acknowledge/resolve items), while Reconciliation in the same
   navigational cluster is SUPER_ADMIN-only. The `attention-center`
   redesign should treat these as distinct surfaces, not one triage hub.
10. **A broken redirect exists on the SALES payment-recording path**
    (`commercial_sales`): SALES holds `payments.create` but not
    `payments.view`; `submit_payment_route` redirects a successful
    submission straight to `payment_detail`, which requires
    `payments.view` — so a SALES user who successfully records a payment
    is immediately 403'd on the very next page load. This is a functional
    bug the redesign must not carry forward, not just a UX rough edge.
