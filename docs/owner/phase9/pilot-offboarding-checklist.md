# Phase 9 — Pilot Offboarding Checklist

Applies both to a planned pilot completion and an early rollback/cancellation.

- [ ] Written decision recorded (extend/convert/end), signed or otherwise formally confirmed by both
      parties.
- [ ] Final data-export offered — via the real Backup & Restore feature (the only real "recovery
      access" mechanism per `export-contract-decision.md`; do not promise an Export feature that
      doesn't exist in the current product contract).
- [ ] License transitioned to the correct terminal state (`SUSPENDED`/`REVOKED`/`EXPIRED` as
      appropriate — real, existing Phase 8 transitions, choose deliberately, not by default expiry).
- [ ] Installation(s) deactivated if the customer is not continuing (real `deactivate` flow, Phase 8V-
      P9's local-deactivation behavior).
- [ ] Any temporary device-slot exceptions granted during the pilot cleaned up / expired (should
      already be time-bound — confirm none were left open-ended).
- [ ] Support access revoked/archived per the internal support owner's own account lifecycle (not a
      new mechanism — normal staff-account offboarding).
- [ ] Pilot's real operational data retention decision made explicitly — per
      `data-classification-and-retention.md`, not left to default/indefinite retention.
- [ ] Post-pilot review completed: what worked, what didn't, feed into the next pilot's onboarding
      checklist if anything should change.
- [ ] If declined/cancelled early: document the real reason honestly (technical failure, customer
      decision, support burden, etc.) — this is real signal for whether Phase 9's pilot-readiness
      claim was accurate, not something to gloss over.
