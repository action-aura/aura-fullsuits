# Phase 9.5B-R — Migration Impact Report

## One additive migration: `338d06dece44_phase_9_5b_r_staff_locale_preference.py`

Chains from Phase 9.5B's head (`af7831a6dc4d`). Adds `owner_staff_users.locale` (nullable `String(8)`) +
a `CHECK` constraint (`locale IS NULL OR locale IN ('en', 'ar')`) — the constraint was hand-added to the
migration since Alembic's default autogenerate does not diff `CHECK` constraints (confirmed: the
autogenerated draft only contained the `ADD COLUMN`).

## Real testing performed

- **Empty database** (`aura_owner_test`): fresh `alembic upgrade head`, exercised by the full test suite's
  own `_migrated_schema` fixture.
- **Populated database**: applied to the real `aura_owner_dev` and `aura_owner_staging` databases (the
  latter still carrying Phase 9's restore-drill data and Phase 9.5A/9.5B synthetic test data) — clean, no
  errors, nullable column needs no `server_default`.
- **Round-trip**: `upgrade → downgrade → upgrade` against `aura_owner_dev`, clean both directions.
- **Schema-drift**: implicit in the full regression (a live/model mismatch fails ORM-level tests
  immediately).

## No data loss, no licensing/financial impact

The new column touches only `owner_staff_users`, adding a single nullable field — no existing row's
existing data is read, transformed, or at risk. `owner_staff_users` has no relationship to `License`/
`Installation`/`Subscription`/financial tables that this migration could indirectly affect.
