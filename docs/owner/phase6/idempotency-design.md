# Phase 6 -- Idempotency Design (Part N)

## Table
`owner_external_idempotency_records`: `idempotency_key_hash` (SHA-256 of the client-supplied key, never the raw key itself), `operation_type` (`ACTIVATION`/`DEACTIVATION`), `request_fingerprint_hash` (SHA-256 of a *safe*, non-secret, non-nonce-varying subset of the request -- product/platform/app_version/installation_id/device_public_key, deliberately excluding the license key, nonce, timestamp, and signature), `result_reference`, `status`, `response_status`, `cached_response_json` (the exact original safe response, replayed verbatim), `expires_at` (7-day TTL).

## Rules enforced
- **Identical retry -> identical result**: `check_idempotency()` returns the existing record when `(key_hash, operation_type)` matches and the fingerprint also matches; the caller returns `cached_response_json` verbatim rather than re-running the operation. Verified live via the simulator pattern and `test_phase6_activation_protocol.py::test_idempotent_retry_returns_same_result_no_extra_slot` (same `response_id`, same `installation_id`, and a direct DB count confirms no second `Installation` row was created).
- **Different payload, same key -> conflict**: `IdempotencyConflictError` (`IDEMPOTENCY_CONFLICT`, HTTP 409) when the key matches but the fingerprint doesn't -- a client reusing an idempotency key for a materially different request is rejected, not silently merged.
- **No device-slot double-consumption**: the device-limit check (Part F) sits *after* the idempotency check in the activation sequence specifically so a replayed/retried request short-circuits before ever reaching the row-lock/slot-count logic.
- **Secrets never stored**: only hashes of the key and fingerprint are stored; `cached_response_json` is the exact same safe, allowlisted response body that was returned externally the first time -- it structurally cannot contain the license key, since the original response never did either.
- **Cross-process correctness**: same story as replay/rate-limiting -- Postgres-backed, so two Owner worker processes handling a retried request from different connections both see the same idempotency record.
- **Explicit transaction boundaries**: the idempotency record is written inside the same commit as the rest of the activation decision (Part E step 23) -- both succeed together or neither does, so there is no window where an activation succeeded but its idempotency record failed to persist (which would defeat the whole point on the next retry).

## A real bug this design caught during development
`deactivation.py`'s original implementation looked up the device key filtered to `status == "ACTIVE"` for signature verification -- but a *retry* of a deactivation request arrives after the first call already revoked that key, so the retry's signature check failed before ever reaching the idempotency lookup, breaking the "identical retry succeeds" guarantee. Fixed by verifying against the *most recent* device key regardless of status specifically for deactivation (`device_identity.py::get_most_recent_device_key`), while check-in correctly continues to require a currently-`ACTIVE` key. See `phase6-test-report.md` for the failing-then-passing test evidence.
